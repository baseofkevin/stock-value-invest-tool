# stock_review_assess —— 综合评估

一批候选票进来，出两样东西：

1. **超级成长股标识**（内部仍叫"硬门槛"、模块里叫 `gates`）——不亏损、增速、
   有供需矛盾。逐条标过 / 不过 / 未核实。
   **只做标识，不排除、不分档、不排序**，而且**只用数据库里现成的数**。
2. **赔率分**（0~15）——谁排在前面。这是**排序**，分低不会让票消失。

两件事刻意分开，而且**不互相打分**：门槛是给人看的判断依据，分数管
"先看谁"。把门槛接进分档只要一行代码，但那样一来工具就替人做了决定——
用户要的是"先看标识、自己去查财报"，所以门槛落到表格的一个列里。

> **命名**：2026-11-20 起，页面上这块叫「超级成长股标识」，表格那一列也从
> 「门槛」改成了「超级成长股标识」。**代码和本文仍叫"硬门槛"/`gates`**——
> 改的是给人看的名字，不是规则。

（"只标识"是 2026-11-20 改的：第一版把门槛做成否决，311 只里 287 只被排除、
「优先研究」直接清零。显示被改掉比不显示更糟，所以退回来只加标识。）

与 `stock_kline_screen` / `stock_quality_screen` / `stock_cycle_elastic` /
`stock_judge_top` 平级：都是顶层包，都**不 import `web`**，都**不自己连库**。
数据由 `web/db.py` 读好，以字典传进来，所以这一层可以单测。

## 代码结构

```
stock_review_assess/            ← 2026-11-20 从 web/review.py 搬出来，与 stock_kline_screen 平级
    config.py    全部阈值（赔率分 + 门槛），一处集中。改一个数刷新页面就生效，没有藏在别处的权重。
    gates.py     三条门槛。纯函数：吃 fin 字典，吐 pass/fail/unknown，按 GATE_KEYS 出结论。
    review.py    赔率分、分档、build()（原来 web/review.py 的内容搬过来）。
    README.md
web/review.py                   ← 只剩 14 行兼容 shim（tests/test_web.py 里 19 个老用例按老名字 import）
web/db.py                       ← 负责取数：merged() / moats() / financials()
```

`stock_review_assess` 不 import `web`、不连库——`inner()` 那五行是复制过来的，
否则 `web/__init__ → app → review` 会成环。数据由 `web/db.py` 读好传进去。

`web/review.py` 只剩一层兼容 shim（`tests/test_web.py` 里 19 个用例按老名字
`from web import review` 引）。新代码请直接 `from stock_review_assess import build`。

**显示哪几条由 `config.GATE_KEYS` 决定**：「算几条」和「显示几条」是同一个开关。

## 门槛：用户原话 → 实现

| # | 用户原话 | 实现 | 数据 |
|---|---|---|---|
| ① | 亏损公司不买 | 扣非 TTM > 0；**单季扣非 > 0**；**扣非/归母 ≥ 80%** | `finance` 的扣非/归母 |
| ② | 主营增速低于 40% 不买 | 单季营收同比 ≥ **25%**，**且**单季扣非增速 > 营收增速 | `finance` 的单季同比 |
| ③ | 无强供求矛盾的不买 | **毛利率环比连升两季**，或**合同负债同比 ≥ 20% 且 ≥ 年化营收 5%** | `OperatingRevenue_Q`/`OperatingCost_Q`、`ContractLiability` |

原方案里的「无新产品/新市场拓展的不买」（第 ④ 条）**整条删掉了**：数据库里没有
"新业务收入"这个字段，判断只能靠手写备注，跟"只用库里有的数据"直接冲突。

第一版试过用 `state/review_evidence.json` 手填，结果是 311 只里 **0 过、311 未核实**——
那张卡永远是 `0/311`，只有噪声。2026-11-20 代码和证据文件一并删掉。要恢复，
得先让 `stock_data_fetch` 把新业务收入抓进库，而不是再加一个手填文件。

### 阈值清单（`config.py` 里就这几个数）

| 常量 | 值 | 含义 | 缺数据时 |
|---|---|---|---|
| `GATE1_DEDUCTED_RATIO_MIN` | `0.80` | 扣非 / 归母 ≥ 80% | **归母 ≤ 0 → 不过**（不是未核实）；**归母缺失 → 跳过这条、仍可能过**；三字段全缺 → 未核实 |
| `GATE2_REV_YOY_MIN` | `25.0` | 单季营收同比下限（%） | 任一同比缺 → 未核实 |
| `GATE3_CL_YOY_MIN` | `0.20` | 合同负债同比 ≥ +20% 记「订单变厚」 | 两期缺一 → 未核实 |
| `GATE3_CL_YOY_FAIL` | `-0.10` | 同比 ≤ −10% 记「订单流失」 | 同上 |
| `GATE3_CL_SHARE_MIN` | `0.05` | 合同负债 / 年化营收下限 | 缺单季营收 → 未核实 |

数据全部来自 `shared.db.finance`，没有第二个来源。

③ 的两条证据**各自独立核实**：三季成本不齐 → 只有「毛利率」那条未核实；
合同负债两期不齐 → 只有「订单」那条未核实；两条都核实不了才整条 `unknown`。

### 三条门槛的完整判定

判定是**顺序短路**的，先命中的先返回（① 的四步见 `gates.py:63-113`）：

```
① 不亏损   1. np_cum <= 0              → 不过（"归母净利润为负：亏损公司不买"）
           2. base = cut_ttm 或（凑不齐四季时）cut_cum；base <= 0 → 不过
           3. cut_q <= 0               → 不过（"当期在失血"）
           4. cut_cum 与 np_cum 都有且 np_cum > 0：
                cut_cum / np_cum < 0.80 → 不过（靠非经常性损益）
           5. 其余                      → 过

② 增速     rev_yoy_q >= 25
          且 cut_yoy_q > rev_yoy_q     （相等也算不过）

③ 供需     (a) gm_q[0] > gm_q[1] > gm_q[2]
        或 (b) cl / (rev_q*4) >= 0.05 且 cl / cl_prev - 1 >= 0.20
        两条一过一不过 → 未核实（不下结论）
        两条都不过     → 不过
        一条不过 + 另一条未核实 → 不过
        两条都未核实   → 未核实
```

`cut_ttm` 拼不齐四季时退回 `cut_cum`（累计扣非），口径不同——这是已知的将就，
见文末「还能改的」。

**① 的三个边界最容易读错**（早先都写错过，已按代码改）：

- **`cut_q` 必须 > 0**，代码是 `cut_q <= 0 → fail`，所以单季扣非**恰好为 0 也判不过**。
  早先写"不为负"是错的。
- **归母 ≤ 0 是"不过"**，不是"未核实"——亏损是**明确的坏消息**，缺数才是**没有消息**。
  早先把两种完全不同的情形混成了一种。
- 归母缺失时 80% 那条被跳过（第 4 步要求 `np_cum is not None`），所以**仍可能判过**，
  只是没法验"利润是不是主业赚的"。这是刻意的（不拿缺数据当否决），但要知道它的存在。

**为什么加 80% 那条**：靠政府补助、卖资产转正的公司，报表上不亏，主业在失血。
「扣非为正」挡不住它，「扣非/归母 ≥ 80%」能挡。

### ② 为什么是 25% 不是 40%

用户的原话是 40%，但照字面执行会筛掉他自己举的那个例子：营收 +33%、
扣非 +75%、Q3 扣非 +161%。模组行业是"老业务价格战拖累总量、新业务爆发"，
总量增速天然低于结构增速。

现在总量这条只留 25% 的底线（`GATE2_REV_YOY_MIN`）。**要回到 40% 就改
`GATE2_REV_YOY_MIN = 40.0`**，代价是拐点型公司全没。

### ③ 供需：只用数据库里有的数

财报里没有字段叫"这个行业是不是供不应求"，所以只认两条能在报表上算出来的证据，
**占一条即可**：

```
(a) 毛利率环比连升两季：gm[0] > gm[1] > gm[2]
    gm = (OperatingRevenue_Q - OperatingCost_Q) / OperatingRevenue_Q

(b) 合同负债同比变厚：cl / (rev_q * 4) >= 0.05  且  cl / cl_prev - 1 >= 0.20
    cl      = 最新一季 ContractLiability
    cl_prev = 去年同季（不是上一季）
```

**a. 毛利率环比连升两季**（当季 > 上季 > 上上季）
分子分母在 `finance` 里（`OperatingRevenue_Q` / `OperatingCost_Q`）。
涨价或产品结构上移会推高毛利率，降价换量会压低它。

**b. 合同负债同比 ≥ 20%，且合同负债 ≥ 年化营收的 5%**
`ContractLiability` 是客户预付的钱，同比（不是环比）比去年同季——合同负债
在 Q4 集中确认，环比比出来的多半是季节性。

两条证据的**合成规则**（行 = 毛利率，列 = 合同负债）：

| | 过 | 未核实 | 不过 |
|---|---|---|---|
| **过** | 过 | 过 | 未核实（打架） |
| **未核实** | 过 | 未核实 | 不过 |
| **不过** | 未核实（打架） | 不过 | 不过 |

三个刻意的取舍：

1. **合同负债用同比，不用环比**。它在 Q4 集中确认，环比比出来的是季节性。
2. **必须过 5% 的占比门槛**。这批 311 只的合同负债中位数只有年化营收的
   **2.4%**，小基数上翻一倍只是噪声（健民集团 3286 万，占营收 1.2%）。
3. **两条打架时不下结论**：毛利率在涨、订单在缩，可能只是原材料降价 →
   落「未核实」，交给人看。

**坚决不加的东西**：提价公告、交期拉长、产能受限。共享库里没有这些字段，
加进来只能靠手写备注，等于把判断建立在数据库之外。金融股没有营业成本、
合同负债也常常不适用，两条都判不了，落 `unknown`。

## 三态与页面呈现

| 状态 | 颜色 | 含义 |
|---|---|---|
| `pass` | 绿 ✓ | 明确满足 |
| `fail` | 红 ✗ | 明确不满足 |
| `unknown` | 灰 ? | 数据缺一季，或两条证据打架。**既不算过也不算不过** |

`unknown` 是第三种状态，页面上单独标出来（灰色小方块）：

* **不是"通过"**。`gate_all_pass` 只数真正 `pass` 的，未核实的不算。
* **也不是"不通过"**。它不扣分、不降档、不进「提示」列——工具不知道的事不替人做决定。
* 顶部三张卡把「过 / 不过 / 未核实」分开数，一眼能看出筛得有多严。

页面上的三处：

* **「超级成长股标识」列**（旧名「门槛」）：每行四个字，`盈利✓ 增速✗ 供需✓`，
  悬停显示阈值 + 读数 + 理由。
* **顶部三张卡**：各自「过 / 不过 / 未核实」只数。
* **汇总行**：`这一批门槛全过 9 只（中粮资本、金科环境、…），明确不过 288 只…`
  ——全过的票直接把名字写出来，超过 12 只显示前 12 只 + 等。

## 数据从哪来

`web/db.py`：

| 函数 | 读什么 | 粒度 |
|---|---|---|
| `merged(conn, date)` | `results.db` 四个工具的结果 | 一只票一行 |
| `moats()` | `shared.db` 的 `annotation`（垄断性） | 全市场 |
| `financials(symbols)` | `shared.db` 的 `finance`（最近 5 个报告期） | 按批取，0.3s |

`financials()` 里的字段（`finance.raw_json` 挖出来的）：

```
rev_yoy_q   OperatingRevenueGrowRate_Q    单季营收同比
cut_yoy_q   NPParentCompanyCutYOY_Q       单季扣非同比
cut_cum     NPDeductNonRecurringPL        累计扣非
np_cum      NPParentCompanyOwners         累计归母
cut_q       cashflow.NPDeductNonRecurringPL_Q   最新单季扣非
cut_ttm     最近四季 cut_q 之和（凑不齐就 None，退回 cut_cum）
gm_q        (OperatingRevenue_Q - OperatingCost_Q) / OperatingRevenue_Q
rev_q       最新单季营收，用来算合同负债占营收的比重
cl          最新一季 ContractLiability（合同负债，预收款）
cl_prev     去年同季的合同负债（同比，不是环比）
```

2026-11-16 批（311 只）覆盖：财务 311/311、单季营收同比 303、单季扣非同比
304、季度成本 292、合同负债两期齐全 299。缺的落到 `unknown`，页面标「未核实」，
不猜。

三条门槛在这一批的结果：

| 门槛 | 过 | 不过 | 未核实 |
|---|---:|---:|---:|
| 不亏损 | 182 | 125 | 4 |
| 增速 | 27 | 276 | 8 |
| 供需 | 63 | 81 | 167 |

供需的 63 只「过」里：9 只两条都满足、37 只靠毛利率、**17 只只靠合同负债**；
另有 8 只因两条打架落「未核实」。

汇总：门槛全过 **9 只**，明确不过 288 只，没有明确不过但还有门槛没核实 14 只
（9 + 288 + 14 = 311，对得上）。

## 分档

分档**只看质量**，和加门槛之前完全一样；标识只出现在「超级成长股标识」列
和顶部三张卡里。

| 档 | key | 条件 |
|---|---|---|
| 排除 | `out` | `Q < Q_HARD(45)`，或命中致命风险 |
| 待补数据 | `nodata` | 这一批没跑质量工具（或这只票失败） |
| 优先研究 | `buy` | 赔率分 ≥ `BUY_CUT`（5），且工具没有判回避/数据不足 |
| 观察 | `watch` | 其余（赔率分不够，或工具自己判了回避/数据不足） |

档内排序也还是老规则：赔率分降序 → 弹性（`strong` 0 / `weak` 1 / `unstable` 2 / 空 3）
→ Q → 代码。门槛不参与排序，名次和加它之前一模一样。

加门槛前后两版的分档都是 **9 / 60 / 86 / 156**（优先研究 / 观察 / 排除 / 待补数据），
一只都没动。

> ⚠️ 这四个数是 **2026-11-16 那批（311 只）当时的页面读数**，**现在没法复算**：
> 那批的 4 份结果已被后续运行覆盖（当前 `results.db` 最新的是 2026-11-20 的
> 35 只那批）。留着它是因为它证明了"加门槛前后分档没变"这件事，而不是当基线用。

> ⚠️ **"工具判回避"是降到「观察」，不是「排除」**（`review.py:434-440`，注释写得很清楚：
> "降为观察而不是排除"）。但 `config.TIERS["out"]["hint"]` 的文案写的是
> 「Q < 45 / 命中致命风险 / **结论就是回避**」，与实际分流不符——所以"排除"到底含不含
> 这一类，**看代码、别信那句 hint**。这也是"排除"计数在不同文档里差 1（287 / 288）
> 的可能来源之一。这一处**没有修代码**（本次只动文档），记在这里待改。

## 赔率分（0~15）

`SCORE_MAX = 15`，七项加分 + 两项扣分。**分低只影响排序，不会让票消失**。

| 项 | 分值 | 判据 |
|---|---:|---|
| 市值小 | 3 / 2 / 1 | `<50 亿` / `<100 亿` / `<200 亿`（`<`，不是 `≤`） |
| 估值低位 | 3 / 2 / 1 | PE/PB/PS 分位均值 `<25%` / `<50%` / `<70%` |
| 周期低位 | 2 | 是周期股**且**产能位置 = `low` |
| 盈利弹性 | 2 / 1 | `strong` 2 分、`unstable` 1 分（`weak` 0 分） |
| 垄断性 | 2 | 有标注且不是「无标注」/「待核实」 |
| 质量 | 2 / 1 | `Q ≥ 80` / `Q ≥ 65`（这一项是 `≥`，方向与前三项相反） |
| 目标价空间 | 1 | `upside ≥ 20%` |
| 趋势走弱 | **−2** | `TREND_PENALTY`，最重的单项扣分 |
| 估值分偏低 | **−1** | `V < V_WEAK(55)` |

3+3+2+2+2+2+1 = 15，正好等于 `SCORE_MAX`。

> **分档只认两项加分以外的门槛**：`Q_HARD` 与致命项。其余加分/扣分都只在排序里体现。
> 这也是"为什么小市值不一定排前、但要扣趋势分"的由来。

## 三件要你拍板的事

**1. 门槛要不要真的排除**

现在是「只标识」。想改成否决，在 `stock_review_assess/review.py: evaluate()` 里加一个
分支即可。建议先只标识跑两周，看你自己会不会照着方块做决定，再决定是否自动化。

**2. 40% 要不要回到总量上**

见「② 为什么是 25% 不是 40%」。一句话：改了就没有拐点型公司了。

**3. 门槛和赔率分的方向是相反的（当前不冲突）**

赔率分奖励"小市值 + 估值低位 + 周期底部 + 弹性强"。高景气股恰好相反：
利润 +161% 的公司 PE 分位往往在 80% 以上，也基本不在周期底部，会被系统性
压到「观察」档。

**当前不冲突**，因为门槛不参与排序——它只是表格里的一列。两套逻辑各说各的：
门槛回答"这生意在不在爆发期"，赔率分回答"先看谁"。

**如果以后要让门槛影响排序**，正确做法不是"门槛加分"（那会把两套尺度混进一个数），
而是在「优先研究」档内开一个"景气优先"的排序开关。

## 还能改的（按性价比）

**P0 数据补全**

| 问题 | 现状 | 建议 |
|---|---|---|
| 没有扣非 TTM 字段 | 最近四季 `NPDeductNonRecurringPL_Q` 求和，缺一期退回累计扣非 | `finance` 加 `NPDeductNonRecurringPL_TTM` |
| 季度成本缺 19 只 | 银行/券商没有营业成本 → 供需永远未核实 | 金融股单独一条判定路径，或标「不适用」 |
| 单季同比每次 parse JSON | 0.3s/批，能接受但白费 | 三个同比落成列 |

**P1 口径将就的地方**

1. **增速只看单季**，容易被并表季度或低基数骗。建议加"两年复合增速"或
   "连续两季 ≥ 25%"。
2. **供需的毛利率用环比**，Q4 集中确认会导致失真。可以改成同比连升两季。
3. **扣非/归母用累计值**，Q1 只有一季，噪声大。等 TTM 字段到位后换口径。

**P2 页面**

* 标识列支持点击筛选（`?gate=supply`）。
* 加一列「证伪信号」：毛利率环连降、增速失速——现在只有买的条件，没有卖的。
* 汇总行的「明确不过」也可以像「全过」一样把名字列出来（现在只有数字）。

## 会咬人的地方

* **低基数**：扣非 +161% 很可能是去年同季在亏损。②挡不住，①能挡一部分。
* **并表**：收入增速里如果有收购来的，②会被骗。看"内生增速"或商誉变动。
* **合同负债的季节性只解决一半**：同比避开了 Q4，但并购并表、单一大单预收
  仍会让同比失真。5% 占比门槛挡的是小基数噪声，挡不了这个。
* **数据源口径**：`raw_json` 是腾讯口径，和东财/同花顺的单季拆分偶有差异，
  对不上时以定期报告为准。

本模块自己的用例在 `tests/test_review_gates.py`；`tests/test_web.py` 里 19 个用例
按老名字 `from web import review` 引，走的是 `web/review.py` 那层 14 行 shim。

**这几条是踩过坑才写下的断言**（`tests/test_review_gates.py` 21 个用例）：

1. `unknown` 不挡买入——否则第 ③ 条永远 `unknown`，整页一只都进不来
   （`test_unknown_gate_does_not_block_buy`）；
2. 两条证据打架时必须落 `unknown`，不能"取更严的"（`test_conflicting_signals_are_unknown`）；
3. 合同负债占比 < 5% 时**不算流失**，只能 `unknown`（`test_small_contract_liability_is_ignored`）；
4. 归母 ≤ 0 必须判 `fail`，不能被当成"缺数据"（`test_losing_company_fails`）；
5. TTM 为正但**单季扣非为负**必须判 `fail`（`test_negative_single_quarter_fails_even_if_ttm_positive`）；
6. 门槛判 `fail` **不改变分档、也不改变名次**（`test_gate_fail_does_not_change_tier` /
   `test_gate_fail_keeps_buy_rank`）——这条是"只标识"承诺的机器看守。

> 七项满分之和 == `SCORE_MAX` 这件事**没有测试守着**。改 `MCAP_STEPS` / `PCT_STEPS` /
> `Q_STEPS` / `ELASTIC_POINTS` 里任一档时，记得手动把 `config.SCORE_MAX` 一起改，
> 否则页面上「11/15」那个比例会算错。

## 一句话

门槛的价值在**逼你先回答三个问题**，不在于让工具替你排除。所以这版把它做成
表格里的一列，而不是一道闸——你盯着那三个方块读财报，比盯着一个"已排除"
的红标有用。
