## 0. 一句话与三条不变式

**一句话**：四个工具各自需要的数据有 70% 重叠，与其各自下载、各自缓存、各自对不上，
不如建一个**按需读写**的共享库——用到哪只取哪只，取过的记覆盖，够了就不再打上游。

改任何设计之前先看这三条，它们决定了绝大多数取舍：

| # | 不变式 | 违反后的后果 |
|---|---|---|
| **1** | **只存不复权的原始值** | 存前复权 → 每次除权整段失效；存后复权 → 与上游对不上，且因子无处可校 |
| **2** | **财报 / 分红 append-only：只增期，不删期** | 上游只回 43 期，删掉的期**永久补不回来** |
| **3** | **数据写入与 coverage 更新必须同一事务** | "数据有了、水位没记"→ 下次重取；更糟是"水位有了、数据没写"→ 误判完整，永久缺数据 |

## 1. 约束与不做的事

真实约束决定了设计长什么样，先摆出来：

| 约束 | 后果 |
|---|---|
| 个人电脑，**不 24 小时开机** | 不能有 daemon、不能有 cron 常驻；所有事必须在"工具运行的那几分钟"里做完 |
| **磁盘有限** | 不能全市场全历史；只留"够用"的深度，其余可删可重取 |
| 四个工具要求**盘后**出结论（盘中价是半成品） | 数据层在盘中只拦"联网取数"，不拦"读库"——库里够用就随时能跑（§6.5 闸 1） |
| 一个人维护 | 依赖只要标准库；迁移脚本能不写就不写；接口越少越好 |
| 上游会限频、会掐连接、会改字段 | 节流必须是"按实测反馈"的，不能是写死的固定间隔 |

**明确不做的事**：

- ❌ 不做全量 hub（不预热全市场）。`ensure` 的语义就是"用到才取"。
- ❌ 不做 daemon / 定时任务。数据在工具运行的那一刻按需补齐。
- ❌ 不做通用迁移框架。只登记**可重入**的那几步（纯新增表 / 加列 / 删索引 / 表重建），
  其余版本不符直接拒绝启动、提示重建（数据全部可再生）。见 §3.5。
- ❌ 不做并发取数。**单线程串行**（理由见 §5.6）。
- ❌ 四个工具**一律不写库**（`last_access_at` 也不写，由数据层自己记）。

## 2. 架构

### 2.1 为什么是"按需中心库"，不是另外两条路

三条路都认真算过：

| 方案 | 好在哪 | 为什么不用 |
|---|---|---|
| A 各工具自己下载 | 零改造成本 | 同一只股票被四份代码各取一遍；口径漂移了没人发现；限频被放大四倍 |
| B 全量 hub（预下载全市场） | 工具跑得飞快 | 磁盘吃不消；首建 30 分钟起步；而且"全市场"里 90% 的股票永远不会被任何工具碰到 |
| **C 按需中心库（选这个）** | 取一次、四工具共用；覆盖可审计；口径只有一处 | 首次运行慢一点（每只 0.42s） |

C 的关键设计是 **coverage 表**：它记的不是"有没有这只股票"，而是"这个域、这只股票、
这个口径，我覆盖到哪一天、有几个洞"。命不命中只看它（§4.1）。

### 2.2 四层模型

```
第 1 层  上游（数据从哪来）    腾讯自选股 / 东方财富 / 通达信 / baostock / 交易所·新浪
第 2 层  传输（怎么拿）        MCP 客户端 / 直连 HTTP / 开源库
第 3 层  适配器（怎么变成行）  stock_data_fetch.sources.<name>.fetch(domain, codes, need) -> Got
第 4 层  路由（该用谁）        router.order(domain) -> [(source, priority), ...]
```

**第 1 层与第 2 层的分离是最重要的一条**：

- `efinance` 的上游是**东方财富**，不是新源。它只是"另一条到东财的传输"。
- `akshare` 一个库里混着**东财 / 新浪 / 乐咕**三个上游，不能整体当"一个源"。
- `baostock` 是**自有库**，是真正独立的上游。

这条直接推出铁律：**同上游的两个传输互相校验，等于自己校验自己**（§5.5）。

### 2.3 一次取数的完整链路

```
hub = preflight()                        ← 六道闸（§6.5），失败直接抛
hub.ensure("kline", "sh600519", need)    ← 唯一会打上游的入口
  ├─ read_coverage → hit? → 返回（0 次上游调用）
  ├─ flock(f"{domain}:{symbol}")         ← 分片锁，不是全局锁
  │   ├─ 双检（等锁期间别人可能已经填好）
  │   ├─ missing_segments(cov, need)     ← 可能多段
  │   └─ for seg: throttle.take → router.fetch → 组级重试
  │              └─ 一个事务里：写数据 + 写 coverage + 写 watermark
  └─ verdict(cov, need)                  ← 要么返回覆盖，要么抛，没有第三种
```

**为什么锁的粒度是 `(域, 股票)`**：全局锁会让四个工具串行；不锁会让同一只被取两遍，
把限频放大一倍。分片锁两头都避开。

## 3. 数据模型

### 3.1 全局规范

**证券标识**：`symbol = 市场前缀 + 6 位代码`（`sh600519` / `sz000858` / `bj430047`），
另存 `exch`（SH/SZ/BJ）与 `setcode`（通达信 1/0/2，调 tdx 直接用，不做二次推断）。

> 不只用 6 位数字：`000001` 同时是平安银行（深）和上证指数（沪），裸数字必然踩坑。

**日期**：一律 `TEXT`，`YYYY-MM-DD`。字符串比较即时间比较，`ORDER BY` 天然正确。
不用 `YYYYMMDD` 整数——省 6 字节/行，但人工排查时看不懂。
`period` 是**报告期末**（`2026-09-30`），不是公告日。

**单位**（最容易出错的一节）：

| 字段 | 单位 | 说明 |
|---|---|---|
| `kline.volume` | **股** | 通达信 `Rows.Volume` 是"手"，入库 ×100；东财 klines 也是手，同样 ×100 |
| `kline.amount` | 元 | 原值 |
| `quote.volume` | **股** | 上游给手，×100 |
| `quote.float_shares` / `total_shares` | **股** | 换手率 = `volume / float_shares`，同单位直接除 |
| `dividend.*_per_share` | **每股** | 上游一律"每 10 股"，入库 ÷10 |
| `finance.*` | **元** | 已实测 `data_finance` 就是元；其他源若是万元，**入库前换算**，`unit` 只做标识 |
| `valuation.total_mv` / `circ_mv` | 元 | — |

**浮点与 NULL**：价格用 `REAL`，比较用相对容差 1e-6，不用 `=`。
`NULL` 表示"上游没给"，**不等于 0**；`0` 表示"上游明确给了 0"。
财报某期只有利润表没有资产负债表时，行仍然存在，balance 字段为 `NULL`——所以命中判定不能只看行数。

**"当期"的定义**：`quote` / `snapshot` 这类快照型，`trade_date` 必须等于**目标交易日**。
判断过期用 `stored.trade_date <> target`，**不用时间差**（长假会误判、周日取的数据周一早上
只差 12 小时却已过期）。

### 3.2 表总览

**13 张表**（schema v6）。R / W / S 三种标记决定了清理策略，必须分开写：

| 表 | 域 | 粒度 | 每只行数 | 可再生 | 清理 |
|---|---|---|---|---|---|
| `stock` | profile | 一股一行 | 1 | R | 跟股票走 |
| `kline` | kline | 一股一日 | 400 | **R** | 滚动 400 根 |
| `finance` | finance | 一股一期 | 43 | **W** | **不删** |
| `finance_revision` | finance | 一股一期一字段 | 0～几条 | W | 不删 |
| `dividend` | dividend | 一股一除权日 | 10–30 | **W** | **不删** |
| `valuation` | valuation | 一股一周 | 520 | **R** | **不删**（体积占比 < 5%，见 §3.5） |
| `quote` | quote | 一股一行 | 1 | **S** | 覆盖 |
| `snapshot` | mainop/consensus/rating/gbalance/gcashflow | 一股一域 | 5 | **S** | 覆盖 |
| `scan` | scan | 一交易日一市场 | —（一日约 5,100 行） | **S** | 滚动 30 天 |
| `annotation` | annotation | 一股一 kind | 1 | W（人工） | 不删 |
| `coverage` | — | 一域一股一口径 | ~6（`scan` 例外：一天一条） | 派生 | 跟股票走 |
| `watermark` | — | 一域一范围 | — | 派生 | — |
| `meta` | — | 键值 | — | — | — |

**R / W / S**：R = 删了能重取；W = 上游窗口滚动或人工录入，**删了就永久消失**；S = 上游不留历史（快照 / 横截面），错过就没有。

`scan` 的"每只行数"没法按股票算——它一行就是一只股票的一天，一天一份全市场。
`annotation` 由人写、不是取回来的，所以清理策略是"不删"：一条 2024 年核实的标注
过了事实有效期也只标 `stale`，不抹掉（§3.3）。

### 3.3 逐表要点

**`kline`** —— 存 raw（不复权），**保留 400 根**（`KLINE_KEEP_BARS`），滚动删除。
`volume` 入库即换成股：`quote.float_shares` 也是股，换手率一句除法就出来，
不用在每个消费点记换算。**一处换算好过十处**。

换算这一步比初稿复杂了：东财 / 腾讯给的是**手**（×100），而 westock 的 `volume`
**单位按板块不一致**——主板 / 创业板是手，科创板（688/689）本来就是股。
所以现在按 `amount / (close × volume)` 逐行判：比值 ≈100 就是手（×100），≈1 已是股（原样）。
这是唯一不依赖"板块 → 单位"硬编码的判据，上游哪天统一单位这里自动跟上；
拿不到 `amount` 时退回 ×100（历史行为，见 `sources/westock._to_shares`）。

**为什么留 400 而不是 300**：最大消费者 `want.kline(bars=300)`（judge_top 要 250、
kline_screen 要 71）。留 400 意味着某只票中间停牌 100 天，最近 300 根仍然完整，
不会出现"要 300 根、库里被裁到 299 根 → 每次去补历史 → 永远补不齐"的抖动。
每多留 100 根约 +35 MB，所以别把默认值再往上调（理由写在 `config.KLINE_KEEP_BARS`）。

**`scan`** —— 一交易日一份全市场横截面（约 5,100 行）。**它不是"一股一档"**：
一行就是"某只股票在某一天"，主键 `(date, symbol)`，查询几乎总是"按日期取整片"，
从不"按股票取历史"。

**列少得反常，是故意的**：只有 `date / symbol / name / close / pct_chg / src`。
市值、净流入、换手率**都不在表里**——要它们就按候选池走 `quote` 域（40 只一批）。
理由是 westock `tool_filter` 的超时是"表达式条件数 × 返回行数"的乘积（实测表在
`config.SCAN_EXPR` 的注释里）：把市值/净流入一起带回来，表达式就从 1 条变 5 条，
全市场口径直接挂掉。而这三个字段只有 kline-screen 对它选出来的几百只要，
拿"全市场少一次请求"换"能不能拿全"，这个交易不划算。

三条设计点：

| 事 | 做法 | 不这么做会怎样 |
|---|---|---|
| 只留 30 天 | `SCAN_RETENTION_DAYS=30`，`hub.prune_scan()` | 5026 行/天 × 250 天 ≈ 1.2 GB/年，是本层唯一会失控的表 |
| `fp` 带日期 | `date=2026-11-13` | 共用一条 fp → 取完周五再要周四，`hit()` 判"已覆盖"然后查出 0 行 |
| 一次一条表达式 | `SCAN_EXPR = intersect([ClosePrice > 0])` | westock `tool_filter` 有约 2 秒服务端硬超时，超时概率是"条件数 × 返回行数"的乘积——想一次拿全市场，表达式就只能有一条（实测表在 `config.SCAN_EXPR` 的注释里） |

**`annotation`** —— 人工标注（目前只有「垄断性」一种 `kind`）。**入库而不是 YAML 文件**：
原来放在 `stock_quality_screen/annotations/moat_annotations.yaml`，跟着代码目录走
（换机器就丢）、改一条要动文本、且四个工具里只有 quality 读得到。

`moat_type` 是**枚举**（8 个值），不是自由文本——它要参与判定（`moat_type != "无标注"`
就是"有垄断性"）。写成自由文本的话「独家资源」「独家 资源」会是两个不同的东西，
而代码只认得其中一个，另一个静默变成「无标注」。枚举里有两项不是结论：

| 取值 | 含义 |
|---|---|
| 6 类垄断（独家资源 / 配额牌照 / 特许经营 / 独家品种 / 技术壁垒 / 网络） | `annotated=True`，参与判定 |
| **`无标注`** | **结论**：查过，没发现垄断性 |
| **`待核实`**（`MOAT_UNVERIFIED`） | **待办**：记录已建、还没读过公告。不加分，报告也不渲染垄断块 |

后者是 2026-11-16 加的：全市场 5000 多只要先各有一条记录，但绝大多数没读过公告，
直接写「无标注」等于谎称"查过了、确实没有"。**覆盖和判定是两件事**，这一列把它们分开。

核实日超过 `ANNOTATION_STALE_DAYS=365` 天只标 `stale` 并显示「待复核」，**不删**：
一条 2024 年核实的「独家品种」2026 年可能已经不独家了，但当年确实独家——抹掉就丢了判断依据。

**`finance`** —— **本 schema 最关键的取舍：一期一行，三表字段并排。**

| 做法 | 优点 | 缺点 |
|---|---|---|
| 三张表分开 | 贴近会计结构 | cycle 要"income + balance 同期对齐"，每次三表 JOIN；判深度要算三张表的最小值 |
| **一期一行（选这个）** | 一次查询拿到一期全部；判深度只看行数 | 列多（18 列）；某表缺字段时该列为 NULL |
| JSON 存一期 | 最灵活 | SQL 里没法按字段筛，quality 的"营收连续三年增长"要全表反序列化 |

口径：**全部存上游原值，库里不含任何我们自己派生的量。**
累计值 `OperatingRevenue`、单季 `OperatingRevenue_Q`、TTM `OperatingRevenueTTM` 三套并列，
上游直接给（实测：本年各季 `_Q` 之和 = 年末累计；TTM = 累计 + 去年年报 − 去年同季）。
列名保持上游原名（零映射风险），未提列的字段留在 `raw_json`（只保留最近 2 期，省 5GB+）。

**`dividend`** —— 复权因子的**唯一**来源，append-only，除权日是既成事实永不修改。
单位一律每股（上游 ÷10）。`plan_text` 存上游原文，便于人工核对。

**`valuation`** —— 唯一需要长历史的域：10 年周频（520 周）。
**入库即周频**：`trade_date` 取该 ISO 周的最后一个交易日，与 quality 的 `_valuation()` 逐点等价。
列名**必须带口径后缀**（`pe_ttm` / `pb_mrq` / `ps_ttm`），否则三种口径混用会让 V 分静默漂移。
⚠️ `pb_mrq` 的分母会随新财报重算，所以本表历史值**不是永不变**：允许整段覆盖刷新，
coverage 不承诺"旧值永久有效"。

**`quote` / `snapshot`** —— 快照型，当期一份。
`snapshot` 是"字段不稳定、只被某一家工具消费"的域（mainop / consensus / rating），
用 `payload` JSON 而不是建三张表：这些域字段随上游变，建表等于给自己挖迁移坑。
`as_of` 的语义**按 domain 固定**：

| domain | `as_of` 含义 |
|---|---|
| `mainop` | **报告期末**（主营构成按报告期披露） |
| `consensus` / `rating` | 目标交易日 |

两个含义混在一列是刻意的：拆成两列会让每行一半是 NULL，查询要写 COALESCE。

**`finance_revision`** —— 上游更正留痕。只在真有差异时写一行（相对差 > 1e-6），量极小。
财报 append-only 不等于"假装上游不会改数"，改了就记下来。

### 3.4 口径指纹 `fp`

`fp` 是"**这份数据是按什么口径取的**"的指纹，进 `coverage` 表，**不含 `src`**：

| 域 | fp |
|---|---|
| `kline` | `fq=raw` |
| `finance` | `type=all;fields=all` |
| `valuation` | `freq=week` |
| `snapshot` | `sub=mainop` / `sub=consensus` / `sub=rating` / `sub=gbalance;p=20` / `sub=gcashflow;p=20` |
| `scan` | `date=2026-11-13`（**带日期**） |
| `dividend` / `quote` / `profile` / `annotation` | 空串 |

两处 fp 必须带参数，方向相反、理由是同一个：**覆盖记录的主键是 `(domain, symbol, fp)`，
fp 一旦表达不出"这是哪一份"，`hit()` 就会拿 A 的覆盖去放行 B。**

- `snapshot` 的五个子域共用一个 `domain`，fp 再不分 → 写完 `consensus` 之后再要 `mainop`，
  `hit()` 返回 True 而按 `domain=mainop` 查出来是 0 行。这是第 5 步测试跑出来的真 bug。
- `scan` 是"一天一份"，fp 不带日期 → 取完周五再要周四，`cov.end=2026-11-13 >= 2026-11-12`
  直接放行，查询查出 0 行、一句告警都没有。**同一类 bug 栽了两次**。

**`fp` 只管"口径变了就作废"，不管"换源了"**。换源要不要作废是另一件事，见 §5.5。

### 3.5 GC、建库、迁移、备份

| 表 | 策略 | 谁触发 |
|---|---|---|
| `kline` | 每股保留最近 **400** 根（`KLINE_KEEP_BARS`） | `hub.prune_kline()` / `maintain --apply` |
| `scan` | 保留最近 **30** 天（`SCAN_RETENTION_DAYS`，可用 `meta['scan_retention_days']` 覆盖） | `hub.prune_scan()` / `maintain --apply` |
| `finance` / `dividend` / `valuation` / `annotation` | **不删** | — |
| `quote` / `snapshot` / `stock` | 覆盖，不增长 | — |

**`valuation` 那一格写"不删"是有意的**：它每股约 520 行、全市场也就几十万行，
体积占比不到 5%；而"10 年"是 `need` 的**取数范围**，不是一条会执行的删除规则。
`maintain` 的注释说得更直接：不删 `finance`/`valuation`/`snapshot`/`quote`——
那些是另外三个工具的燃料。真要为它设裁剪，得先想清"删了以后分位还准不准"。

**GC 不是数据层自动做的，是工具跑完时显式调一次**（当前挂在 `stock_kline_screen/pipeline.py`
收尾，两句 `hub.prune_scan()` / `hub.prune_kline()`，失败不抛；也可以直接跑
`python3 -m stock_data_fetch.maintain --apply`）。写成"每次写入后"会让人以为
`ensure` 会顺手裁——它不会：写入路径上一次多删几百行，等于把一次取数的成果扔掉。

清理粒度是**股票**，不是表：删半只股票的数据会造出 coverage 与实际不一致的状态，
要修就得重取——等于白删。删完 `PRAGMA incremental_vacuum`（建库时已设 `auto_vacuum=INCREMENTAL`）。
`annotation` 加进"保留"那一列不是随手写的：它是**人工投入**，删了就没人愿意再填一遍。

**建库**：`preflight()` 自动完成，工具第一次跑就会建好。DDL 在包内 `schema.sql`。

**迁移**：`user_version != 6` 时先看这一跳在不在白名单里：

| 情况 | 动作 |
|---|---|
| 库不存在 | 按 `schema.sql` 建（`user_version = 6`） |
| 版本可逐跳升（`db.AUTO_UPGRADE`，当前 v1→v6 全覆盖） | **自动迁移**，整个升级包在一个事务里，失败就停在旧版本、重跑一次即可 |
| 白名单里没有的一跳 | **拒绝启动**（`SchemaMismatch`），提示备份后 `rm` 重建 |

自动迁移只对"纯新增表 / 加列 / 删索引 / 可重入的表重建"开放，每一条都要先回答
"重复执行两次会不会出错"。改列类型、拆表那种变更在 SQLite 里做不到幂等，仍然只能重建——
所以第 1 步那条"一律不写迁移脚本"的结论，落地时收窄成了"只写可重入的那几步"。

**备份**：`./run.py backup` 对 `shared.db` / `results.db` 各做一次 `VACUUM INTO`，
校验完整性后按份数清理旧档（默认留 **7** 份，`--keep` 可改）。
`VACUUM INTO` 是原子快照，比 `cp` 安全（`cp` 可能拷到正在写的页），顺带整理碎片——
实测同样内容体积小很多。**它不自动跑**（没有 daemon），要放在你的跑批习惯里，
比如每周五收盘后。`results.db` 也在备份范围内，否则"结果一起被复制、越滚越大"就是它自己。

### 3.6 交易日历：文件，不进库，而且要是"长"的

日历是**规则**不是数据：进库就要维护更新，反而多一个失效点。它承担三件事——
盘中闸判定"今天是不是交易日"、`target_date()` 决定"取到哪一天为止"、
日频域的 hole 判定。

**它同时是所有域的深度上限**，这一点最容易被忽略。原来的日历继承自 kline-screen
（`2022-11-14 起，970 天`），对 300 根 K 线够用，对估值不够——而它不会报错，
只会让 `need.start` 被静默夹到 4 年前，再以"点数不足"的名义失败。

所以现在**只有一份，项目内自己生成**：

| 路径 | 跨度（2026-11-17 当前值） | 谁生成 |
|---|---|---|
| `state/trading_calendar.json` | **12 年：2014-11-07 .. 2026-11-17，2923 个交易日** | `python -m stock_data_fetch.build_calendar` |

**2026-11-17 取消了"兜底那份 4 年日历"**。原来 `DEFAULT_CALENDAR` 指向
`~/MyData/stock-kline-screen-tool/database/trading_calendar.json`——那个仓库 11-15
改名成 `stock-value-invest-tool` 之后目录就不存在了。日常运行看不出问题
（`Config.from_env()` 走 `resolve_calendar()`，本来就优先用项目内这份），但任何
**直接构造 `Config()`** 的路径——首当其冲是六个测试文件——都会在 `TradingCalendar.load()`
抛 `HubNotReady`，于是 `python3 -m stock_data_fetch.tests` 整体报错。

现在 `DEFAULT_CALENDAR = state/trading_calendar.json`，跟着 `HUB_ROOT` 从包的物理位置推导，
不依赖别的仓库是否还在。文件不存在时给的是明确的一句"交易日历不存在… 先跑 build_calendar"，
**不是悄悄退回 4 年深度**——4 年会让估值必然 `InsufficientDepth`，而错误信息看起来像数据缺失
（§6.6 那个坑就是这么来的）。

生成后与旧日历对过账：**旧有新无 = 0**（4 年那份完全被包含），新有旧无 = 1951（历史部分）。
`--no-merge` 会跳过并集、直接用新抓的覆盖——除非你确认要变短，否则别用。

选择发生在 `Config.from_env()`（不是 `preflight()`）：`Config()` 必须保持确定性，
否则测试结果取决于机器上有没有生成过文件。`STOCKHUB_CALENDAR` 显式指定时优先于它。

**生成**（需联网，收盘后跑）：

```bash
python -m stock_data_fetch.build_calendar                   # 12 年，自动选源（westock → szse → eastmoney）
python -m stock_data_fetch.build_calendar --dry-run         # 只校验不写盘
python -m stock_data_fetch.build_calendar --source szse     # **权威腿**：深交所按月，144 次请求
python -m stock_data_fetch.build_calendar --source westock  # 12 次请求，够快
python -m stock_data_fetch.build_calendar --source eastmoney # 1 次请求，但经常被掐
```

三条腿的差别是实打实的，按"语义 → 代价"排：

| 源 | 一次能给多少 | 语义 | 备注 |
|---|---|---|---|
| westock `data_trade_calendar` | 按年分页，**12 次请求给 12 年** | **日历本身**：直接答"哪天开市"（`isTrading`） | 默认主源 |
| 深交所月度日历 | 一月一问，**144 次** | **权威**：`jybz` 0/1 由制定者给 | 与 westock 那份逐日对账过，见 §5.4 |
| 东财 `push2his`（`sh000001`） | **1 次给 12 年 2900 行** | **间接证据**：指数那天有 bar 就推"开市了" | 突发配额用完会整段拒连（§5.7） |

顺序不是"哪个稳用哪个"而是**语义优先**：拿"指数有没有成交"去推"市场开没开市"绕了一层，
所以它排在最后——只在另两条都不可用时才用。2026-11-14 生成时就撞上东财封禁期（连拒 30 分钟），
换成 westock 的日历接口之后反而更对。

所以 `build()` 默认与已有日历**取并集**：一次"备用腿的运行"不该把 12 年截短。
跨度不足 10 年会打印告警（不阻拦写盘）——写一份 5 年的日历也比没有强，
只是估值会以 `InsufficientDepth` 收场。

**写盘前必过校验**（`check()`）：整年交易日数落在 `[230, 260]`、单日断档 ≤ 12 天、
末日距今天 ≤ 10 天。首末年不参与年度计数（首年从年中开始、末年只到生成日）——
这条是踩出来的：第一版用 `[230,260]` 卡所有年份，于是 `--years 12` 在任何时候
都报"2026 年 210 个交易日，明显偏少"。

## 4. 命中、缺口与异常

### 4.1 命中判定（唯一依据）

```
hit(cov, need) :=
      cov 存在
  AND cov.fp              == fingerprint(domain)
  AND cov.partial         == 0
  AND cov.end_date        >= need.end
  AND blocking_holes(cov) == 0        ← 只数非 permanent 的洞
  AND cov.n               >= need.min_*  ← 深度只由点数表达
  ── 仅 dividend ──
  AND cov.start_date      <= need.start  ← 唯一看 start 的域
```

三处与初稿不同，都是实现时被测试逼出来的：

| 初稿 | 现在 | 原因 |
|---|---|---|
| `holes == 0` | `blocking_holes == 0` | 停牌股的洞永远不会消失。按旧判据 → 永远不命中 → 每次跑白打一次上游还要等 168 小时。`permanent` 洞仍计入 `coverage.holes`，只是不阻塞 |
| 看 `start` | **不看 `start`** | 次新股永远凑不满"回溯 300 根"，按 `start` 判会让它每次运行都重取一次、永远不命中。"够不够用"由 `min_*` 表达 |
| — | `n >= need.min_*` | 门槛由**调用方**声明：quality 20 期、cycle 40 期、judge 6 期。混在一起就会重犯"20 期刚好过门槛却静默降级"的老坑 |

**绝不判断"表里有没有这只股票的行"**：有行不等于覆盖够——`finance` 可能只有 20 期
（够 quality、不够 cycle），`kline` 可能只有 207 根（够 kline-screen、不够 judge）。
判断错了不会报错，只会安静地输出一份"看起来正常"的报告。

### 4.2 区间与点数分离

`Need` 里 `start`/`end` 决定**取多长**，`points`/`min_points` 决定**够不够用**，两者不许混。
混在一起就会重犯老坑：20 期刚好过门槛，静默降级出一份看起来正常的报告。

**有两个域天生只有一个端点**，实现时必须让 `None` 合法，否则它们一次都不会取数：

| 域 | 缺哪一端 | 为什么 |
|---|---|---|
| `finance` | `start = None` | "最近 43 期"，起点由上游定，我们说了不算 |
| `dividend` | `end = None` | 除权日没有上界，问到哪天算哪天 |

第 5 步之前的代码在两处都写了 `if need.start and need.end`，于是 `finance` 首次运行
`segs` 恒为空、一次上游都不打，最后报"库里没有覆盖记录"——症状看起来像网络问题，
实际是一行条件判断。

### 4.3 洞的节拍：不是所有域都按交易日算

`merge()` 要用交易日历重算"应有一天都没少"，这条只对**日频**成立。第 5 步之前它对所有域
一律执行，于是季度序列（`finance`）被拿去和"每年 250 个交易日"比，算出一个覆盖全程的
巨型洞 → `blocking > 0` → `hit()` 永远 False → 每次运行都重取，永远不命中。
这个 bug 藏了整整两步，因为当时只测了"分红 0 条"——那种情况下 `end` 是 `None`，
`recount_holes` 提前返回了。

| 节拍 | 域 | 怎么算洞 |
|---|---|---|
| `day` | `kline` | 按交易日历重算：区间内每个交易日都该有一条 |
| `period` | `finance` | **不算洞**。缺期由 `n >= min_points` 与 `end` 兜，单季缺失由 `quarter` 标 `missing` |
| `week` | `valuation` | **不算洞**。上游最多 454 周、门槛 430 周，缺 24 周以上点数就不够了，`n` 已经说明问题 |
| `event` | `dividend` | **不算洞**。十年不分红是合法状态，`holes` 这个概念在这里不存在 |
| — | `quote`/`snapshot`/`profile` | **点域**，一股一份，走 `merge_point()`，没有区间 |

### 4.4 缺口（hole）与退避

洞有两种粒度：**段落级**（`start..end` 整段缺）与**点位级**（中间少一天）。
每个洞带 `retry / next_try_at`，退避 **1 / 6 / 24 / 72 / 168 小时**，5 次仍空 → `permanent`。

**`permanent` 洞不阻塞命中**（否则停牌股永远不可用），但必须出现在报告里——
`Range.permanent_holes` 会带出去，工具可以逐股跳过。

**`settle()`**："这只票这一段本来就没有数据"和"这次没取到"在返回值上**长得一模一样**（都是空 `rows`）。
区分办法只有再问一次：**同一次运行里同一段取两次都空 → 认账判 `permanent`**，
不再走 1/6/24/72/168h。这把"停牌股每次烧 6 次重试"压成 2 次。
代价是"真·临时故障"会被误判——但临时故障多发于整源层面（限频、断连），
会被 router 拦在更外层，落不到 `settle` 这里。

**`merge_coverage` 只重算、不增量**，且区间语义**按域分两种**：

- `dividend`：`start` 记"我们查过的最早一天"（十年不分红是合法状态，0 行也要记查过）；
- `kline` / `finance` / `valuation`：区间**就是库里数据本身的范围**，不保留旧边界。

> 为什么必须分：K 线是滚动删除的。若对所有域都保留 `old.start`，GC 删掉老 bar 之后，
> 下次 merge 会拿一段"已经不存在了"的区间去重算缺口，凭空造出一个假头部缺口；
> 这个假缺口还要重试 6 次才 `permanent`，期间每次运行都 `blocking > 0` → 不命中 → 白打上游。

### 4.5 `verdict()`：异常的唯一定判出口

多个条件同时成立时抛哪个？必须有确定顺序，否则用例没法离线断言：

```
partial                     → PartialData          （限频截断，已取到的留库，下次接着补）
有阻塞洞                     → InsufficientDepth    （299 根不能当 300 根用，哪怕门槛只有 250）
只剩 permanent 洞 + 点数不够 → HoleUnreachable      （**唯一允许调用方逐股跳过的异常**）
其余                        → InsufficientDepth
```

有了它，`ensure` 才是"要么拿到覆盖、要么拿到异常"，没有第三种返回。
**这条边界一旦放宽，工具就开始出"缺几只股但看起来正常"的报告**——崩溃会被重跑，错报告会被拿去用。

### 4.6 异常树

异常只回答"发生了什么"，不回答"该怎么办"。该怎么办由调用方决定——四个工具的取舍本来就不一样。

| 异常 | 码 | 含义 |
|---|---|---|
| `MarketOpenError` | 2 | 处在交易时段，半成品 bar 不能当收盘价 |
| `HubNotReady` | 3 | 库打不开 / PRAGMA 没落实（多半网络盘、只读盘） |
| `SchemaMismatch` | 3 | `user_version` 不符，拒绝启动 |
| `InsufficientDepth` | 4 | 区间够但点数不够 / 有阻塞洞。**绝不降级返回部分数据** |
| `PartialData` | 5 | 限频重试后仍缺。已取到的已落库，下次接着补 |
| `EmptyResult` | 5 | 上游空表且不属于"次新 / 停牌"两种合法空 |
| `ThrottleTimeout` | 6 | 等配额或冷却超时 |
| `FactorError` | 7 | 复权数据自相矛盾（`P_ref <= 0` 等），**不允许跳过** |
| `HoleUnreachable` | 8 | 永久缺口导致点数不足，唯一允许逐股跳过 |
| `SourceUnavailable` | 9 | 源不可达（缺令牌 / 鉴权 / 接口变更 / 持续空表）。**只在 router 内部流动**，不该到达工具 |

## 5. 节流与源路由

### 5.1 令牌桶：按返回行数，不按请求数

实测结论：**限频的计量单位是"返回行数"，不是"请求数"，也不是"固定间隔"。**
间隔与成功率**非单调**（0.5s 能过，1.0s 反而失败），所以"每个源一个固定最小间隔"是错的。

```
take(src, rows):
    持 flock ── 读桶 ── 算够不够 ── 不够就睡 ── 扣 ── 写桶 ── 放锁
```

**必须先放锁再睡会透支**：先算后睡，睡醒后再扣，两个进程会同时通过检查。
所以整个"读-算-睡-写"必须在一个 flock 里。

| 参数 | 值 | 说明 |
|---|---|---|
| `RATE_ROWS_PER_MIN` | westock **200000**；eastmoney / tencent 15000；tdx / baostock 0 | 0 = 不走令牌桶，只用最小间隔 |
| `MIN_INTERVAL_MS` | westock **1000**；eastmoney 400；tencent 200；tdx 300 | 见下面"两个闸管的是两件事" |
| `BURST_ROWS` | 12000 | 桶容量。一批 60 只 × 200 根 = 12000，得让一批一次拿满 |
| `THROTTLE_BUDGET` | 300s | 单次 `take()` 累计等待上限，超了抛 `ThrottleTimeout` |

**westock 的速率从 15000 提到 200000（2026-11-15），同时把最小间隔从 0 提到 1000ms。**
两个改动听着矛盾，其实是在说两件事：

- 令牌桶按**返回行数**计费。`kline` 走多码批量后单请求 40 只 × 300 根 = 1 万行，
  按 15000 行/分钟算就是 1.5 请求/分钟——**等于把批量卡死了**，批量省下的时间全还回去。
- 但 westock 的真实限频不是按行数，是**按每分钟请求数**（实测约 60~70 次/分钟）：
  `quote` 一只一行、`kline` 增量一只一行，令牌桶永远满的、请求却一秒十几个，
  服务端直接回"限频"（实测：`quote` 整池 3271 只 = 82 批，前 66 批成功、后 16 批全 None）。
  1000ms 正好压在 60 次/分钟。

所以**两个闸管的是两件事**：令牌桶管"别在短时间内吃掉太多行"，最小间隔管"别把请求数打爆"。
只留一个都会出问题——这正是"按实测反馈，不按固定间隔"的具体形状。

> **已知边界 bug 与修法**：单次申请行数 > 桶容量时 `tokens >= rows` 永不成立，
> 循环到预算耗尽 → 进程挂死（不报错，看起来像卡住）。修法是"超过桶容量就按桶容量计费"，并告警。

### 5.2 冷却闸：限频反馈

固定间隔治不了配额耗尽，唯一可靠的信号是**上游自己报的限频**：

| 状态 | 取值 |
|---|---|
| 首次冷却 | 30s（实测 6s 就能恢复，但持续请求会立刻再触发，故取 30） |
| 连续触发 | ×2 递增，上限 300s |
| 一次干净返回 | 减半 |
| 连续 3 次干净 | 清零 |

**冷却 ≠ 不可用**：路由排序时冷却中的源**排到后面**，不是摘掉；一个都不剩就干等。
按"冷却中→跳过"的写法，主源一进 300s 冷却，整批 20 只股票集体报"没有可用源"——
**故障面从"变慢"扩大成"全部失败"**。

**瞬断也按限频处理**：`RemoteDisconnected` / 超时 / 5xx 这类 transient 错误**不换源**，
而是冷却 + 重试同一源，连断 3 次才抛 `ThrottleTimeout`。
换源等于把压力转给另一家、同时把数据换成另一家的口径。

### 5.3 组级重试：只重取失败的那几只

westock 把一次请求**内部按 10 只一组**拆开独立判定，失败组在 `errors[]` 里自报：

```json
"metadata": {"total": 119, "successCount": 110, "errorCount": 9},
"errors": [{"symbol": "sh600179,sh600182,...,sh600192",
            "code": "BATCH_ERROR", "message": "查询dayK线异常：... msg=服务限频"}]
```

所以 **`partial` 的判据是 `errorCount > 0`**，不是"请求清单减返回清单"——
后者只能告诉你少了谁，不能告诉你"为什么少"，而限频要退避、退市要记永久洞，动作完全不同。

| 规则 | 做法 | 理由 |
|---|---|---|
| 只重失败组 | 按 `errors[].symbol` 拆回去重取 | 重取整批等于把配额再花一次 |
| 重试前必须 `penalize` | 先冷却再取 | 原工具是"丢码就拆半立刻重取"，实测这会让限频**加重**（连发 6 批全败） |
| 最多 3 轮 | 3 轮后仍失败 → 这些 symbol `partial=1` | 不无限重试 |
| 粒度是 symbol | 失败者各自 `partial=1`，成功者正常推进 `end_date` | 整批 partial 会让已拿到的数据白等下一次 |

**交易所（深交所 / 上交所）与巨潮资讯能补什么**

| 接口 | 结果 | 给得出什么 |

| `szse.cn/api/market/ssjjhq/getTimeData?marketId=1&code=000001` | ✅ 200 JSON | **当日快照**（开高低收、成交量），只有当天 |
| `www.szse.cn` 历史日线 | ❌ 无此接口 | — |
| `cninfo.com.cn/new/data/szse_stock.json` | ✅ 200 JSON | 全市场 `code` / `orgId` / 简称 |
| `cninfo.com.cn/new/hisAnnouncement/query` | ✅ 200 JSON | 公告全文检索（含 `announcementId`、`adjunctUrl`） |
| `cninfo.com.cn/data20/...` | ❌ 404 | 路径随改版变，不稳定 |
| `query.sse.com.cn/*` | ❌ 502（本机网络） | 换网络再验 |

结论很干脆：**它们不能替代东财/腾讯做出行情和财报，但可以当日历的权威腿**。

- **行情**：交易所只给"当日快照"，没有历史日线下载 → `kline` 300 根无从谈起；
- **财报**：定期报告是 PDF/HTML，没有结构化三表 → 东财/westock 才是结构化源；
- **估值**：交易所根本没有 PE/PB → 只能自己算（总市值 ÷ 净利润），多一层口径风险；
- **分红**：只有"权益分派实施公告"原文，要解析 PDF 才拿得到"每 10 股派 X 元、除权日哪天"；
- **日历**：✅ **唯一一个它是权威、别人都是转述的域**，而且给的是逐日 0/1 判定，
  不是"某指数有没有 bar"这种间接证据。

所以只有日历接了交易所（`--source szse`），其余域的用处是**人工核对时的索引**：
`probe` 报分红不一致时，去巨潮按公告标题搜"权益分派实施公告"就能看到原文。

**深交所日历与我们的 12 年日历逐日对过账**（2026-11-14，抽查 11 个月，跨 2016/2020/2024/2025/2026）：
**10 个月完全一致**，唯一差异是当月——深交所已排到月末，我们的日历只到生成日。
用 `--source szse` 独立生成 12 年（144 次请求）再与 westock 那份取并集，
**新增 0 天**：两个完全独立的源（交易所 vs 腾讯）逐日一致。

**为什么 `kline` 主源最后是 westock（2026-11-15 定，中间换过两次）**

三个源都比过，结论是"谁都没有一条腿走到黑"：

| 源 | 好 | 差 | 现在的位次 |
|---|---|---|---|
| `westock` | **多码批量**（40 只/请求，增量 60），raw 口径，`amount` 有值 | 令牌要自己管（宿主内存里拿不到） | **主** |
| `eastmoney` | `fqt=0` 无鉴权，一次给全历史（茅台 6042 行、2001-08-27 起） | `batch=1` 逐只 HTTP，4304 只实测 **50–75 分钟**；且突发配额用完整段拒连 | 第一备 |
| `tdx` | raw 与东财逐点相同 | OAuth Bearer 只在宿主进程内存，独立 CLI 进程直接 `401 Missing Bearer authorization`——**架构上不可执行** | 备（读到令牌才启用） |
| `tencent` | 无鉴权、一次 900 根、真 raw | 单只；WAF 轮换封禁；`amount` 没有（落 0） | 第二备 |

**换主源那次的实际原因不是"哪家更准"，而是"哪家能批量"。** 两个源的 `priority` 都是 0，
兜底排序键又带 `name`，字典序 `"eastmoney" < "westock"` —— 于是东财永远排第一、
westock 一次都没被选中过（实测日志：一次全量 2923 条 eastmoney 请求、**0 条**真正用到 westock）。
现在由 `sources.PREFERRED["kline"] = ("westock", "eastmoney", "tencent", "tdx")` 显式定序，
东财退为第一备源。

**换源没有作废任何旧数据，依据是下面 §5.5 那条铁律**：raw 就是交易所成交价，
三家的差异只在分位四舍五入（格力 2026-08-26 `41.58`；比亚迪 2025-07-28 `337.00`、
07-29 `111.42`——三家一致），所以 `fp` 一动没动。

### 5.5 三条铁律

**① 换源要不要作废旧数据？——不放 `fp`，放 `meta`。**

先明确 `fp` 的唯一作用：决定"库里的数据还能不能用"。所以"`src` 进 `fp`"能做的只有一件事：
**我们换了源，就让旧数据作废**。问题于是变成：换源后新旧数据混在一条序列里，出不出事？

| 域 | 混得起吗 | 要作废吗 |
|---|---|---|
| `kline` raw | **混得起**：raw 就是交易所成交价，差异只在分位四舍五入 | 否 |
| `quote` / `snapshot` | 一股一行、每次覆盖，**不存在"混"** | 否 |
| `dividend` | 除权日是既成事实，两家不会给两个日期。**混不了**（真风险是"漏一次"，靠探针） | 否 |
| `finance` | **有影响**：东财不直接给 `_Q` 与 TTM，切过去会出现"有的期有单季、有的期没有" | 是 |
| `valuation` | **影响大**：分位对尾部极敏感，混进一段另一家的 `PE_TTM`，十年分位会跳 | 是 |

**结论：`fp` 不加 `src`。** 改用 `meta['domain_src:<domain>']`，在 `ensure` 里比一次：
需要作废的域（valuation / finance）发现源变了 → 该域整段重取；其余域只补洞与向前延伸。

可追溯性不靠 `fp`：知道"这段数是谁给的"由**行级 `src` 列** + `coverage.src` 承担；
知道"发生过降级"由 `meta('source_degraded', ...)` 承担。`fp` 不是审计工具。

**另加一条轻纪律**：换源时**只允许补洞与向前延伸，不允许覆盖已有 bar**。
否则两家的数会在"拼接期"被静默改写——这件事 `fp` 和 `meta` 都拦不住。
代码里落成 `ON CONFLICT ... WHERE kline.src = excluded.src`：同源可纠正，异源只补空缺。

**② 校验必须跨上游。** `a.upstream != b.upstream` 是探针成立的前提。

| 探针组合 | 结果 |
|---|---|
| efinance vs 东财直连 | ❌ **假校验**：同源，误差恒 0，什么都验不出来 |
| akshare `stock_zh_a_hist` vs 东财 | ❌ 假校验（这条就是东财） |
| baostock vs 东财 | ✅ 真校验 |
| tdx vs westock | ✅ 真校验（复权双样本误差 0.00） |

如果拿 efinance 去"验证"东财，跑出来 100% 一致，会得出"数据可靠"的结论——
而东财哪天改口径，两边会一起改，探针永远不会报警。**同源校验比没有校验更糟**，它给的是假的安全感。

**③ 开源库是可选依赖，只做校验和第三备。** 基础设施不能因为 `pandas` 升个小版本就整体启动失败。

| 规则 | 做法 |
|---|---|
| 可选依赖 | `try: import akshare except ImportError: AVAILABLE=False`，源自动从路由摘掉，**主链路零影响** |
| 版本钉住 | `requirements-optional.txt` 写 `==`，不写 `>=` |
| 不做主源 | 主源只用 MCP 与直连 HTTP |
| 失败即禁用 | 某源连续 3 次抛异常 → 本次进程内禁用，记 `meta` |

### 5.6 单线程串行（已定）

| 通道 | 源 | 计量 |
|---|---|---|
| A | westock | 返回行数（令牌桶 200k/分钟）+ **请求数 ≤ 60/分钟**（1000ms 间隔）；实际瓶颈是后者 |
| B | eastmoney（直连 + efinance） | 返回行数；实际瓶颈是"连取 20 只后被掐" |
| C | tdx | 未知；独立进程无令牌 |
| D | baostock / akshare | 探针用，量极小 |

**不并行的三个理由**（按重要程度）：

1. **并行的收益是"快 3 分钟"，代价是排查成本翻倍。** 限频的长尾会让并发与限频的因果关系极难分离。
2. **四个工具本身串行跑**，单次只需要"候选池里的几十只"，不是"全市场同时拉"。
3. **串行天然满足"节流器是唯一串行点"**。多线程后 flock 与令牌桶仍能工作，
   但"谁在等谁"从一条线变成一个图。

串行不等于放弃通道抽象：`throttle.take(src, rows)` 本来就按源计量。
**将来真要并行，改的是 `api.py` 里一个循环的形状，不是数据结构。**

### 5.7 限频实测（这一节比参数更重要）

**westock**：限频表现为 `metadata.errorCount > 0` + `errors[]` 自报，是**组级失败**，不是整批拒绝。
真实瓶颈是**每分钟请求数**（约 60~70），不是行数——所以它的节流是"令牌桶 + 1000ms 最小间隔"两道闸
（§5.1），跨进程会叠加（单进程刚好，双进程打穿）。

**东财 `push2his`**：五轮才定性——

| 轮次 | 做法 | 结果 |
|---|---|---|
| 1 | 连取 20 只（`beg=1990` 全历史） | 第 20 只左右开始 `RemoteDisconnected` |
| 2 | 换 `User-Agent` | **无效**，照样断 |
| 3 | 间隔拉到 1.0s / 1.5s | **仍然全断**（说明不是速率滑窗） |
| 4 | 静默几十秒后重试 | **恢复**（说明不是 IP 封禁） |
| 5 | 2026-11-14 密集取数两轮后再试 | **8 个不同 URL 全部 0.2 秒内关闭，持续 20 分钟以上未恢复** |

**结论：突发配额，用完就掐 TCP（不返 429），与请求速率无关。**
恢复时间**不是常数**：静默几十秒有时够，密集用过一个小时后半小时也不一定够。
所以"取数失败"和"这个源坏了"必须分开处理——前者等，后者换。

三个后果：

1. `RemoteDisconnected` 是 `OSError` 子类，**`URLError` 接不住**，漏接会让它裸穿到工具；
2. 它属于 transient → 重试同源，**不降级**（换源会把口径换成另一家的，还要作废旧数据）；
3. **但"瞬断"不能直接罚冷却**。实测 10 只 K 线跑了 336.5 秒，其中 240 秒纯等冷却，
   而真实取数只要 4 秒（干净状态下每只 0.35–0.44s）。掐一次连接的成本是 0.4 秒，
   罚 30 秒（连掐翻倍到 60/120/240）是 75 倍惩罚，且同批里 8 只连续成功说明它是**偶发**的。
   现在 `Router._call()` 第一次瞬断**立刻重发一次、不冷却**，第二次起才进冷却退避。

**westock `data_kline`（kline 主源，2026-11-15 接入）**：按 `start` / `end` 区间取，
另带 `limit = points + 20` 给 `min_bars` 门槛留缓冲，所以"要 300 根就给 300 根"没问题。
口径三件事都实测过（与库内 tencent raw 逐点比对，`sh600519`）：

| 项 | 实测 | 处理 |
|---|---|---|
| 价格 | 不传 `fq` 返回的就是 **raw**（1439.1 / 1480 / 1446.44… 与库内同值） | 直接落库，不作废任何旧数据 |
| `volume` 单位 | **按板块不一致**：主板 / 创业板是手，科创板（688/689）是股 | 按 `amount/(close×volume)` 逐行判，统一成股（§3.3） |
| `amount` | **有值** | 补上这一列（tencent 通道没有，落库恒 0） |

另两个细节：`last` 是收盘（落库前改名 `close`），返回**倒序**（新→旧），适配器排回升序。

> 早先（2026-11-14）试过一次 `data_kline` 只回 **1212 根（≈5 年）**、`limit=5000` 也一样，
> 当时的结论是"当不了 K 线主源、甚至当不了 raw 备源（当时以为它只给前复权）"。两个判断
> 在 11-15 都被推翻：给它 `start/end` 就按区间取，不传 `fq` 给的就是 raw（与库内 tencent
> raw 逐点同值）。所以正确的说法要分两句——**它不能当"一次给全历史"的源**（日历因此不用它），
> **但按区间取 300~400 根正合适，而且能多码批量**（K 线因此用它）。

**`tencent`（`web.ifzq.gtimg.cn` 的 `fqkline/get`）**：无鉴权、一次 900 根、
`fq` 段留空就是**真原材料**。2026-11-14 与东财 `fqt=0` 逐点对过账
（5 只票 × 300 根，OHLC + 成交量，**bad = 0**），所以它换源不作废任何旧数据。
两个坑：元组顺序是 `[date, open, close, high, low, volume]`（第 3 位是**收**盘），
而且**没有成交额字段**——`kline.amount` 是 `NOT NULL`，只能落 0，靠 `src` 区分。

**tdx**：`POST initialize` 直接 `401 {"error":"unauthorized", "error_description":"Missing Bearer authorization"}`。
令牌在宿主内存里，不落盘。**宿主里"连接器已登录"不等于独立进程能拿到令牌**——
2026-11-14 实测：WorkBuddy 里 westock / tdx / 妙想三个连接器都显示已连接，
独立的 `python -m ...` 打 `txmcp.tdx.com.cn` 仍然 401，`127.0.0.1` 的 MCP 代理也
401（那是宿主给会话内工具用的短令牌，不是给脚本用的）。所以本层必须自备凭据
（westock 的令牌文件）或走无鉴权通道（东财、腾讯、深交所）。

### 5.8 降级与留痕

```
router.order(domain) 的顺序：
  1 该域所有 AVAILABLE 且未被禁用的源，按 priority 升序
  2 冷却中的源**排到后面**；全都冷却就等（take 会睡到冷却结束）
  3 主源连续 3 次失败 → 本次进程内降级，记 meta('source_degraded', ...)
  4 返回 partial → **不降级**，走组级重试（换源解决不了限频）
  5 返回 transient → 先无冷却重发一次；仍断则冷却（**上限 = base，不翻倍**）后重试；
     连断 3 次 → **有备源就降级**，没备源才抛 ThrottleTimeout
```

**第 5 条在 2026-11-14 深夜又改了一次**，两次都是被真实故障逼出来的：

| 版本 | 规则 | 为什么改 |
|---|---|---|
| 初版 | 连断 3 次 → 抛 `ThrottleTimeout`，**绝不换源** | "限频不是源坏了"，换源会把压力转给另一家 |
| 第二版 | 瞬断先重发一次、不冷却；之后冷却**但上限压在 `cooldown_base`** | 东财整段拒连时冷却翻到 300 秒，每批股票先干等 5 分钟（§5.7） |
| 现在 | 连断 3 次 → **有备源就标死并降级**，没备源才抛 | 实证：东财被封 40 分钟期间，腾讯通道就闲在旁边，而按旧规则 4300 只的候选池会变成"每隔 30 秒冷却到期就有一批股票失败"——工具拿到的是一份**少了若干只却不报错**的报告 |

判断依据留在代码里：`_call` 里已经重发过一次、冷却过一次、连试三次了，
"这个源此刻不可用"的证据足够硬；`meta['source_degraded']` 会留痕，
告诉后来的人"这段 K 线是腾讯给的，因为东财当时整段拒连"。

**限频不是"源坏了"**。只有"源不可达 / 接口变更 / 持续空表"才降级。
降级必须写 `meta`：`{"domain":"finance","from":"westock","to":"eastmoney","reason":"...","at":"..."}`。
不写的话，三个月后没人知道库里这段数哪来的。

**空表不是降级，也不是成功**：东财 `data: null` 与 `klines: []` 都返回 200，
20 只样票里占 3 只。它走 `empty_reason`（`no_data` / `code_moved` / `param_error`），
由 `coverage.settle()` 决定记洞还是认账。

> 六个源里有四个在参数写错时返回空表而不报错。所以**空表的原因只能由适配器判断**——
> 上层无法区分"停牌"和"我传错了参数"，而这两者一个该记永久洞、一个该报错。

### 6.1 公开 API（`Hub` 上 19 个方法，按用途分四组）

### 6.2 `ensure` / `ensure_many` / `read`

| 函数 | 语义 | 写库 | 打上游 |
|---|---|---|---|
| `ensure` | 保证"覆盖 + 无阻塞洞 + 够点数"，否则抛 | 是 | 可能 |
| `ensure_many` | 批量，**不抛单只失败**，失败进 `Batch.failed` | 是 | 可能 |
| `read` | **只读**：不满足也照样返回现状，绝不因为参数写大了就去打上游 | 否 | 否 |

`ensure_many` 必须显式消费 `Batch.failed`：非空且不调用 `raise_if_any()` 也不看它，
`doctor` 会警告，收盘汇总里也必须打印失败只数。

**三条硬规则**：

| 规则 | 原因 |
|---|---|
| 拿不到深度就 `raise`，**不返回部分数据** | 返回部分数据 = 让工具出"看起来正常"的报告，这是最坏的结果 |
| `partial` 时不推进 `end_date` | 否则下次命中会认为"这段已完整"，永久缺数据 |
| 锁粒度 `(domain, symbol)` | 全局锁让四工具串行；不锁让同一只被取两遍，限频放大一倍 |

### 6.3 复权（`factor` / `adjusted`）

```
r_d       = P_prev / P_ref(d)
P_ref(d)  = (P_prev − cash + rights × rights_price) / (1 + bonus + transfer)
factor(t) = Π_{d ≤ t} r_d
qfq(t)    = raw(t) × factor(t) / factor(anchor)
```

**为什么算"因子"而不是直接算前复权价**：因子只跟除权事实有关，与锚无关；`raw → qfq` 是比值，
锚一变整列都变。拆开的好处是**幂等**（窗口向前滚动、旧除权日掉出窗口时，分子分母同时少一个 `r`，
比值不变——同一根 bar 今天和三个月后的前复权价一致）与**可缓存**（缓存 `(d, r)` 列表，
与调用方传什么日期无关）。

**窗口外的除权日可以跳过**：`factor(t)/factor(anchor)` 里，起点之前的所有 `r` 严格抵消。
但**必须区分两种情况**：

| 情况 | 处理 |
|---|---|
| 除权日早于最早一根 bar | 合法跳过（抵消），记 debug 日志 |
| 除权日在窗口内、但前一日没有 bar | **抛 `InsufficientDepth`**——这是数据缺口，跳过会让 qfq 整段偏高且看不出来 |

**四条守卫**：

| 守卫 | 做法 | 不这么做的后果 |
|---|---|---|
| 每 10 股 → 每股 | 入库即 ÷10 | 除数 3.0 变 21，已踩过 |
| 除权日非交易日 | 取 `ex_date` 及之前最后一个交易日 | 撞假期时因子整段错位 |
| `bonus/transfer/cash` 全 0 | `r = 1`，跳过 | 无 |
| `P_ref <= 0` 或 `cash >= P_prev` | 抛 `FactorError`，**不允许跳过** | 跳过会让 qfq 静默偏高，且看不出来 |

**两个入口的锚默认值不同，是刻意的**：
`factor.adjusted()` 锚**最后一根 bar**（同样输入必须同样输出，否则没法离线断言）；
`Hub.adjusted()` 锚 **`hub.target`**（工具要的是"和今天可比"）。
两者只在"最后一根 bar 之后又发生过分红"时才有差别——而那正是最容易忘的情形。

**只缩放 OHLC，不动 volume/amount**：量不会因为送股而变小，且换手率要"未复权量配未复权价"才对得上。

### 6.4 `single_quarter`（第 5 步）

上游 `_Q` 为空时的兜底，优先级：库里 `_Q` 非空 → 该期是 Q1 就直接取累计 → 上期存在且连续就差分 →
**上期缺失则记 `missing`，不填 0**。

填 0 会让下游的"同比""环比"算出一个看起来合理的数，而那个数是假的。

### 6.5 六道闸 `preflight()`

```python
hub = preflight()
```

| # | 闸 | 判定 | 失败 |
|---|---|---|---|
| 1 | **盘中** | 交易日 09:15–15:05 → **标记 `intraday=True`，不拦启动**；联网时才拦（见下） | `MarketOpenError`（只在 `ensure` 内） |
| 2 | 库可用 | 不存在且允许建 → 按 `schema.sql` 建 | `HubNotReady` |
| 3 | 版本 | `user_version != 6`。在白名单（`db.AUTO_UPGRADE`）里就**自动逐跳迁移**，不在才拒绝 | `SchemaMismatch` |
| 4 | PRAGMA | 回读 `journal_mode` 必须是 `wal`（网络盘会静默退回 rollback） | `HubNotReady` |
| 5 | 日历 | 文件在、没断档、没过期（>30 天） | `HubNotReady` |
| 6 | 空间 | 低于 500MB **只告警不拦**（清理是 GC 的职责） | — |

**闸 1 在 2026-11-14 改过语义：从"启动就拦"改成"联网才拦"。**

原来的写法是盘中直接抛，于是四个工具在 09:15–15:05 完全不可用——哪怕它们要的数据
昨天就在库里、这一次一个上游请求都不用打。这和"按需数据层"的定位是冲突的：
数据层存在的意义就是"取过一次就不取"，而**"现在需不需要取"与"现在能不能取"是两件事**。

| 情形 | 盘中能不能跑 |
|---|---|
| 库里有且够新（`hit` 命中） | **能**，全程只读库 |
| 缺数据，但 `need.end` 严格早于今天（补历史） | **能**（2026-11-17 起）；K 线/扫描/财报/估值/快照等历史域放行 |
| 缺当日或未来数据 → 必须联网 | **不能**，`Hub.check_online()` 在 `api._pull()` 里抛 |
| `quote`（实时行情，无历史版本） | **不能**，即使 `need.end` 是昨天 |
| `allow_intraday=True`（`STOCKHUB_ALLOW_INTRADAY=1`） | 能，但会在 `meta` 里留痕 |

拦截点挪到 `api._pull()` —— 那是**唯一**决定"要不要打上游"的地方。放在那里才和真实意图一致：
不是"不许开始"，而是"不许取数"。副产品是盘中运行时 `target_date` 自然退到上一交易日，
所以"盘中看昨天的数据"是自洽的，不会拿出半成品 bar 冒充收盘价。

`ensure_many()` 遇到 `MarketOpenError` **立刻整批中止**，不收进 `failed`：那不是"某一只失败"，
收进去的话 4000 只股票就是 4000 条同样的提示，第一条之后全是噪音。

**这个函数必须只做本地、离线、毫秒级的判断。** 启动路径一旦依赖网络，上游抖一下四个工具就都起不来；
跨源日历对账因此放在 `probe` 里，不在这里。

盘中闸的边界取 `09:15`（含集合竞价）与 `15:05`（给收盘集合竞价与上游落库留 5 分钟），
且 `CLOSE_GRACE` **必须与闸上界同一个值**，否则会出现"闸放行了、目标日还是昨天"这种说不清的错位。

### 6.6 各域的 need 规格

| 域 | need 形态 | 深度 | 消费者 |
|---|---|---|---|
| `kline` | `want.kline(cal, end, bars=300, min_bars=250)` | 要 300 根（库保留 400） | kline-screen（71）、judge-top（250） |
| `finance` | `(periods=43)` | 43 期（上游上限） | cycle（40 TTM）、quality（20）、judge（6） |
| `dividend` | `(since = kline 起点 − 1 年)` | 覆盖 K 线全程 | judge-top |
| `valuation` | `(years=10, min_weeks=430)` | **430 周 ≈ 8.3 年**（上游上限 454 周） | quality-screen |
| `quote` | `(target_date)` | 当期 | kline-screen / quality / judge |
| `profile` | `(无上界)` | 取过一次就不再问 | quality / cycle |
| `snapshot` | `(子域, as_of=target)` | 当期（`gbalance`/`gcashflow` 是 20 期） | quality / cycle |
| `scan` | `want.scan(day)` | **一天一份全市场**（约 5,100 行） | kline-screen 粗筛 |
| `annotation` | 不走 `ensure`（人工写，`annotation` 模块 + CLI） | 一股一条 | quality（垄断性加分） |

`scan` 的 `points=5100` 是**预计返回行数**（估上游配额用，不是"期望几个点"），
门槛 `min_points=1`：横截面只要有一行就算取到，真正"空"的情况由适配器报 `empty_reason`，
不该靠点数猜。它的 `fp` 带日期（§3.4），覆盖记录**一天一条**。

**`valuation` 的门槛是 430 而不是 520**（2026-11-14 冒烟改的）。东财
`RPT_VALUEANALYSIS_DET` 对茅台最早一行是 2018-01-02（2150 个交易日 = 454 周），
这是数据源的天花板。写 480 的结果是 3/3 全败、且报错写成"库 205 / 需 480"——
看起来像数据缺失，其实是**两个真因叠在一起**：

1. 交易日历只有 4 年（2022-11-14 起），`want.valuation` 拿
   `cal.on_or_after("2016-11-15")` 去对齐起点，二分查到的插入点是 0，
   返回**日历首日**而不是 `None`，于是 `need.start` 被静默改成 4 年前；
2. 就算日历够长，上游也只有 8.9 年。

**两条都改掉了，而且改法是"分开表达"**：

| 问题 | 修法 | 现在的行为 |
|---|---|---|
| 起点被夹到日历首日 | `start` **不再夹日历**：日历覆盖十年才用它对齐到交易日，不够长就直接用自然日 | 日历 12 年（2014-11-07 起）→ 起点 = "10 年整那天之后的第一个交易日" |
| 门槛不可达 | 按上游上限定 430 | 要更长必须**换源**，不是调大这个数 |

判断"日历够不够长"的那句条件是 `cal.days[0] <= day`（`need.valuation`）。写错它的后果很隐蔽：
2014-11-07 起的 12 年日历让这个条件恒真，于是"短日历"那条分支只能靠测试自己造一份短日历来覆盖
（`test_coverage` 里两个分支各有一条断言，`test_westock.test_valuation_depth` 正向钉"起点落在
10 年窗口边上、不是日历首日"）。

**`profile` 刻意不带 `end`**：元数据一年也变不了一次，按交易日判过期意味着 quality 每次跑
都要把候选池的行业全重取一遍。`end=None` 在 `hit()` 里等于"不看过期"，取过就够；
真要刷新用 `ensure(..., force=True)`。

**`snapshot` 的 `as_of` 记的是"哪一天问的"，不是 `mainop` 报告期**：`mainop.as_of` 是
报告期末（内容属性），拿它去跟交易日比会永远"末端不足"，每次运行都重取。
报告期本身存在 `snapshot.as_of` 列里，消费者照样能拿到。

### 6.7 运维四件套：`doctor` / `probe` / `repair` / `maintain`

四个工具的定位完全不同，**跑错时机会把维护动作变成日常依赖**：

| | `doctor` | `probe` | `repair` | `maintain` |
|---|---|---|---|---|
| 网络 | 一次都不打 | 必须打 | 必须打 | 一次都不打 |
| 写库 | 绝不 | 绝不 | **会写**（默认 dry-run） | **会写**（默认只审计，`--apply` 才动） |
| 回答什么问题 | "库自己有没有坏" | "库和上游/另一家源对不对得上" | "库里的历史行能不能修" | "这些数据该不该留、删了会怎样" |
| 什么时候跑 | 四个工具启动前随手跑 | 换源、换口径、怀疑数据时手动跑 | `probe` 报 MISMATCH 之后 | 库大了、启动变慢时手动跑 |
| 退出码 | 有 `ERROR` → 1 | 有 `MISMATCH` → 1 | 恒 0 | 恒 0 |

四个都不进 `preflight()`。启动路径一旦依赖网络，上游抖一下四个工具就都起不来；
而 `repair` / `maintain` 会改数据，更不能自动触发。

**`maintain` 与 `doctor` 的分工**：`doctor` 问"**能不能用**"（不变式、覆盖、闸门），
`maintain` 问"**该不该留**"（体积、孤儿覆盖、冗余）。`--apply` 会做四件事：
升 schema（删 `ix_kline_date` 省 33 MB）、收编 `fp=''` 的孤儿覆盖、`scan` 留 30 天、
`kline` 留 400 根，最后 `VACUUM` 把页还给文件系统。
它**不删** `finance`/`valuation`/`snapshot`/`quote`，也不删 `finance.raw_json`——
那 6.6 MB 是"解析器以后改好了能重算"的唯一来源，删了就得重拉全市场财报。

### `doctor`：只读体检（`mode=ro`，一条写语句都没有）

```
python3 -m stock_data_fetch.doctor            # 人读
python3 -m stock_data_fetch.doctor --json     # 给脚本
```

体检工具顺手改了库，就没法拿它当"体检"了——所以连接是 `mode=ro`，库不存在时**报 ERROR
而不建库**。它查 8 类事：库与版本 / 日历跨度 / 各域概览 / 四条不变式 / 深度门槛 /
水位线 / `meta` 留痕 / 磁盘。**最值钱的是"不变式 3"**（数据与 coverage 同事务）：

| 裂法 | 症状 | 为什么危险 |
|---|---|---|
| `coverage.n` ≠ 表内行数 | 少报/多报行数 | `hit()` 只看 `n` 和洞，照判"命中" |
| `coverage.end_date` ≠ `MAX(date)` | 覆盖推进了、数据没跟上 | 明天起永远差一天，且永远不报错 |
| 有覆盖、没数据 | 命中但查出 0 行 | 工具拿到空表当"没有信号" |
| 有数据、没覆盖 | 数据在但没人认领 | 下次重取一遍，白花配额 |

四种都是**静默**撒谎：工具照跑、报告照出，只是数据悄悄少了一截。

### `probe`：跨源对账（五个探针）

```
python3 -m stock_data_fetch.probe --calendar         # 只跑日历
python3 -m stock_data_fetch.probe --db .testtmp/smoke/shared.db
python3 -m stock_data_fetch.probe --valuation --symbols sh600519,sz000858
```

（注意：`--calendar` 是"跑日历探针"，日历文件路径用 `--calendar-file`。）

| 探针 | 比什么 | 抓到过什么 |
|---|---|---|
| `calendar` | 本地 vs `data_trade_calendar`（唯一权威：它直接说哪天开市） | 本地多算/少算交易日 |
| `qfq` | 本地 `factor` 前复权 vs 上游前复权，逐点 | 见下面的口径说明 |
| `dividend` | 本地 vs 上游**按除权日聚合后**的值 | **同日多方案漏记**（库里 1.0 / 上游 1.2） |
| `valuation` | 本地周频 vs 东财 `RPT_VALUEANALYSIS_DET` 原始行 | — |
| `suspension` | 洞是停牌（上游也没有）还是我们缺数据（上游有） | — |

三档结论：`OK` / `MISMATCH` / `SKIP`。**退出码只反映 `MISMATCH`**——上游被封、库里没这只票，
都是 `SKIP`，不该让维护脚本变红。

**三条踩出来才有的设计**：

1. **按探针各自挑票。** 第一版全按"K 线行数最多"挑票，于是 `--valuation` 在三只没有
   估值的票上连报三次"库里没有估值"——看起来像探针坏了，其实是从来没探到。现在
   `qfq` 挑 K 线最全的、`valuation` 挑估值最多的、`suspension` 只挑**有洞**的。
2. **某条探针一次都没跑起来就明说**，不要"0 通过 0 不一致 0 跳过"这种空账。
3. **`qfq` 窗口必须跨过一次除权日。** 前复权是"每个点乘一个系数"，窗口内没有除权日时
   两边乘的是同一个系数，比值恒等于 1，**怎么错都"一致"**——实测漏 0.2 元/股的那次，
   最近 30 根 bar 全部一致。现在起点会自动拉到最近除权日之前再退 10 个交易日。

### `qfq` 为什么要算两种口径再比

前复权有两套算法，**数不一样**，而两边都自称"前复权"：

| 口径 | 除权日之前怎么算 | 用它的 |
|---|---|---|
| 等比（乘因子） | `P × (p_ref/p_prev)` | **本库 `factor`** |
| 等差（减派现再除送转） | `(P − 派现 + 配股价×比例) / (1 + 送转)` | 东财 `fqt=1`、westock `fq=qfq` |

两者在**除权日当天锚点相同**（都等于除权参考价），差异只出现在更早的日子，幅度约
`派现 × (1 − 当日价/前收盘)`。实测（`sh601318`，2026-11-14）：一笔 0.98 元派现落在
56 元股价上，2026-07-02 那天本地 48.0679、上游 47.9400——**差 0.27%，这不是错，是口径**。

这里踩过一次坑：一开始假设"东财是等比、只有 westock 是等差"，于是把东财当严格裁判。
实测下来**两家都是等差**，探针因此天天报假警。猜"哪家用哪种口径"两边都致命：

- 把口径差当数据错 → 天天报假警，最后没人看；
- 把数据错当口径差 → 放宽容差，漏记的分红永远查不出来。

所以现在**本地把两种口径都算出来**：上游能对上任意一种就通过（并写明对上了哪种），
两种都对不上才是数据问题。容差也不能纯相对：上游只给到"分"，一股 50 元的票
分位取整就有 1e-4 的相对误差，所以绝对差在半分钱以内的一律不算差异。

**这条探针验的是"数据"不是"公式"**：上游能对上"由我们的分红 + 除权日 + 前收盘推出来的
等差序列"，说明这三个输入是对的；而 `factor` 的等比公式本身对不对，归 `test_factor`
的单元测试管——外部没有同口径的源可以当裁判。

### `repair`：修被 append-only 卡住的漏记

```
python3 -m stock_data_fetch.repair dividend                      # dry-run，只看
python3 -m stock_data_fetch.repair dividend --symbols sh601318 --apply   # 真写
```

`dividend` 是 append-only（`_write_dividend` 一条都不改），那条规矩防的是"上游改数"。
但"同日多方案只记了一条"不是上游改数，是**我们记漏**——而 append-only 让它重跑
`ensure` 也修不好，`probe --dividend` 会年复一年报同一条。

所以补一条**窄口径**通道，只在能证明"库里这条是上游若干分之一"时才动手：

    同一除权日，上游 >= 2 条方案，
    且库里的 (派,送,转) **恰好等于其中一条**，
    且上游合计**大于**库里的值
    → 改写成合计。

认不出这个签名就不碰（换源差异、上游真改数、我们真多了钱，都留给人的眼睛）。
每次改写往 `meta` 写一行 `dividend_repair/<symbol>/<ex_date>`：旧值、新值、上游各条原文、
时间——日志会滚掉，`meta` 跟库走。改完显式清 `factor` 的进程内缓存（签名含 `updated_at`，
但"改了值却没变行数"正是最容易骗过缓存的情形）。

## 7. 口径裁定（6 条，附实测依据）

| # | 争议 | 裁定 | 依据 |
|---|---|---|---|
| 1 | `finance` 金额是元还是万元 | **元** | 茅台 2026-09-30 累计营收 `130,970,743,649` = 1309.7 亿，只有"元"成立 |
| 2 | `valuation.pe` 是 TTM 还是静态 | **TTM / MRQ / TTM**（`PE_TTM` / `PB_MRQ` / `PS_TTM`） | 与 quality 的 `V` 分口径逐点对齐，混用会让分位静默漂移 |
| 3 | `industry` 用申万还是上游原值 | **上游原值，不做申万归一化** | 归一化要维护一张映射表，而四个工具只用到"是不是金融/是不是同一个行业"这种粗粒度。顺带：这推翻了"43 期是零余量"的旧论证——43 期真的是零余量，所以门槛写 `>= 40` |
| 4 | `mainop` 的 `trade_date` 语义 | 其实是**报告期** | 主营构成按报告期披露，没有"交易日"概念 |
| 5 | 同一除权日有两条方案怎么办 | **相加，不是二选一** | 上游把"年度分红"和"特殊分红"拆成两条，共用 `exDiviDate`（`proposalSn` 1/2）。见下 |
| 6 | 前复权用等比还是等差 | **等比**（除权参考价连乘） | 等比下"收益率可乘"，10 年分位才可比；等差会让长周期收益率略偏高。代价是与两家上游（东财 `fqt=1`、westock `fq=qfq`，**都是等差**）的数字天然差 `派现×(1−价/前收盘)`，所以 `probe` 把两种口径都算一遍再比，见 §6.7 |

**第 5 条的实测原文**（westock `data_dividend`，2026-11-14）：

    sh601318  2018-06-07  10派10.000（有分红） + 10派2.000（特殊分红）  = 1.200 元/股
    sz300750  2024-04-30  10派20.110（有分红） + 10派30.170（特殊分红） = 5.028 元/股
    sz300750  2026-04-22  10派21.780（有分红） + 10派47.790（特殊分红） = 6.957 元/股

按方案逐条写库时，`(symbol, ex_date)` 主键让后一条 `ON CONFLICT DO UPDATE` 掉前一条，
于是宁德 2026 少记 2.178 元/股（**-31%**）、2024 少记 2.011 元/股（**-40%**）、
平安少记 0.2 元/股。复权因子随之偏大，历史收益率被系统性抬高约 1–2 个百分点——
而日志里只留一句"与库里不一致"，看起来像上游改了数。
现在 `_dividend_rows()` 按 `ex_date` 聚合求和，`plan_text` 用 ` + ` 拼接（审计要能看出是两条），
`(plan_text, 派/送/转)` 全等的视为重复下发、不重复累加。

**把"上游更正"处理成"覆盖 + 留痕"**：财报是 append-only（只增期不删期），但上游改数时会
`UPDATE` 该期的值，同时往 `finance_revision` 写一行（相对差 > 1e-6 才写）。
这样"最新值"永远只有一份，历史变更可查。

**分红仍是真 append-only**（`_write_dividend` 一条都不改）：除权日是既成事实，
改它比留它更危险。但"改不了"不等于"发现错了只能删库"——上面那个 bug 的存量数据走
`repair dividend`（§6.7）：只在"库里的值恰好等于上游其中一条方案、而上游合计更大"时
才改写成合计，并往 `meta` 留痕。这不是给 append-only 开口子：那不是上游改数，
是我们当初少记了一半，补回去不改变任何一个既成事实，只补上当初漏掉的那一半。

- 人为删掉中间一天 → `InsufficientDepth`，**不返回 299 根**；

- 上游连续 3 次失败后第 4 只**不再白打上游**（`strikes` 必须跨股票累积）；
- 盘中补历史（`need.end` 早于今天）→ 放行；盘中要当日/未来数据 → `MarketOpenError`，且**一次上游都没打**；`quote` 始终拦；
- 同一除权日的两条方案 → 派息 `6.957`（不是 `4.779`），且 `plan_text` 两条都在；
- 估值起点落在"10 年整那天之后的第一个交易日"，**且不早于 10 年整**——日历短于窗口时则原样保留自然日，

- 只缺最后一天 → 只请求那一天，且起点是**覆盖末端之后的下一个交易日**（`_next_trading` 的主线；
  日历末端不够时才退回自然日 +1）；
- 第一次瞬断 → 第 2 次就成功、**冷却一次都没睡**（基准 30s，睡过就不算"立刻"）。

> 其余几行的单价仍然是 westock 批量下测的，继续有效；`finance`/`dividend` 不支持多码的
> 那部分（分红逐只）也没变。

2. **估值永远 `InsufficientDepth`** → 4 年日历 + 静默夹取 + 不可达门槛，三者叠加（§6.6）；

（恒为 `None` → 令牌续期时 `urlopen(None)` 抛 `ValueError`），以及 `snapshot` 三个子域
共用一条覆盖记录（写完 `consensus` 之后 `mainop` 永远"命中"却查出 0 行）。

## 10. 已知遗留

| 项 | 现状 | 何时处理 |
|---|---|---|
| **两家上游都是等差口径** | 实测东财 `fqt=1` 与 westock `fq=qfq` 都是"派现直接减"，只有我们是等比。`probe` 用"本地算两种口径、上游对上任意一种即通过"消化这个差——但这也意味着 **等比公式本身没有外部裁判**，只能靠 `test_factor` 的单元测试 | 若将来要外部验证等比公式，得找一家用等比的上游（理杏仁/聚宽），先验口径再接 |
| **baostock 不可用** | `bs.login()` 返回 `10001011 黑名单用户`（网络侧被拒）。因子金标准与估值独立校验两条暂时落不了地 | 换网络/换机器再试 |
| **`factor` 的探针跑不了自动化** | 因子校验基准是 tdx qfq 价格，而 tdx 在 CLI 进程 401。`纪要` 那次是手工调的宿主 MCP | 手工季度跑，或等 baostock |
| **东财封禁时长未知** | 密集取数后 `push2his` 会整段拒连（0.2s 内关闭），2026-11-14 实测**持续 20 分钟以上未恢复**，而"静默几十秒恢复"是稀疏取数时的表现 | 长跑测出恢复曲线，再决定 `cooldown_*` 要不要按次数而非时间退避 |
| **`amount = 0` 有两种含义** | `tencent` 通道没有成交额字段，而 `kline.amount` 是 `NOT NULL DEFAULT 0`，只能落 0。于是 0 既可能是"上游明确给了 0"，也可能是"这一行来自腾讯通道"。区分只能看 `kline.src`。而 `judge_top` 的换手折算与 `kline_screen` 的 `turnover20` **现在都读 `amount`** | 换过源的股票在那段拼接期里 `amount` 会从 0 变有值，指标会跳一下。要干净就按 `probe` 对账后整段重取；或让指标显式跳过 `amount = 0` 的行 |
| **估值只能到 8.9 年** | 东财 `RPT_VALUEANALYSIS_DET` 最早 2018-01-02（454 周），门槛已按此定 430 | 要"十年分位"必须换源（理杏仁/tdx），先验口径再定 |
| **长日历是生成物，不会自己变长** | `state/trading_calendar.json` 的末日停在生成那一天（当前 2026-11-17），往后不再长。闸 5 会在"末日距今天 > 30 天"时报 `HubNotReady`，`doctor` 另有 `cal.short` 告警 | 写进季度维护清单：`python3 -m stock_data_fetch.build_calendar` 重跑一次（12 次请求，取并集，不会变短） |
| **股票级 GC 没有实现** | `stock.last_access_at` 一直在写（`touch_access`），但**没有任何代码按它回收数据**——`grep "DELETE FROM stock"` 零命中。原设计里那句"`last_access_at` 早于 90 天 → 删该股 `kline`/`valuation`"只是设想，相关注释已于 2026-11-17 改成"只写不读" | 真要做时注意：删 `kline` 必须同事务重算 coverage，否则 `hit()` 会拿一条指向空表的覆盖去放行 |
| **东财空表比例** | 20 只样票 3 只空表（15%）。若成立，4300 只里有几百只永远取不到 | 全市场量级再验；`ensure_many` 已能跳过而不是整体失败 |
| **停牌股段级重试** | `settle()` 会多重试一次（整段 + 缺口段共 3 次调用） | 已接受，写进断言 |
| **`valuation.circ_mv` 恒为 NULL** | 东财 `RPT_VALUEANALYSIS_DET` **没有流通市值列**（`CIRCULATE_MARKET_CAP` / `CIRC_MARKET_CAP` / `FLOAT_MARKET_CAP` / `FREE_MARKET_CAP` / `NOTLIMITED_MARKET_CAP` 全部返回 `9501 字段不存在`）。`total_mv` 有（`TOTAL_MARKET_CAP`）。**不拿 `total_mv` 顶替**：对不全流通的股票那是个偏大的数，会让换手率偏小 | 真要就用 `quote.circ_mv`（westock 有），或其他报告名，先验再用 |
| **`mainop` 每次运行都重取** | 覆盖 `as_of` 记的是"哪一天问的"，隔天就过期。这是有意的（问的是"有没有新披露"），代价是每天每股 1 个请求 | 若测得浪费，改成"报告期 + 披露截止日"判过期 |
| **`tdx` 令牌落盘** | 宿主若将来落盘，`available()` 自动启用，无需改代码 | 等 |

### 10.1 全市场价格/估值快照**不在本层**（2026-11-17 拆出）

曾经在 `stock_data_fetch` 里加过第 8 个域 `price`（schema v7），当天就拆走了：
抓全市场一天只有 6 个上游请求、不需要 hub / router / coverage / throttle 那一整套，
更不该让"取一天价格"被这里的 schema 版本闸卡住。现在它在独立的
**`stock_price_show`** 包里，本层回到 `SCHEMA_VERSION = 6`。

同样的 `STOCK_SHARED_DB` / `STOCK_RESULTS_DB` / `STOCKHUB_CALENDAR` 环境变量名），

### 11.2 术语

| 词 | 含义 |
|---|---|
| **域（domain）** | 一类数据：`kline` / `finance` / `dividend` / `valuation` / `quote` / `profile` / `snapshot` / `scan` / `annotation` |
| **上游（upstream）** | 数据真正的来源方：tencent / eastmoney / tdx / baostock |
| **传输（transport）** | 怎么拿到：mcp / http / lib。同一个上游可以有多条传输 |
| **need** | 一次取数需求（区间 + 点数门槛 + 口径指纹） |
| **coverage** | 覆盖记录：某域某股某口径，覆盖到哪天、几个洞、是否 partial |
| **fp** | 口径指纹：决定"库里这份数据还能不能用" |
| **hole** | 缺口。段落级或点位级，带退避状态，5 次仍空 → `permanent` |
| **partial** | 限频截断后的标记。**不推进 `end_date`**，下次接着补 |
| **blocking_holes** | 非 permanent 的洞。命中判定只看它 |
| **空表（empty_reason）** | `no_data` / `code_moved` / `param_error` / `new_stock` / `suspended` |
