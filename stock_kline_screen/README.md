# K 线选股 · v2.0（共享数据层版）

> `stock-kline-screen-tool`（v1.10，westock CLI 直连 + 自管 JSON 缓存）的重建版。
> **七条规则一字未动**，取数全部改走共享库 `stock_data_fetch`——缓存、限频、重试、
> 覆盖判定、复权因子全部下沉，这一层只剩「怎么裁决」。
>
> - 版本：v2.0（`__version__ = "2.0.0"`，`RESULT_VERSION = "v2.0"`）
> - 代码：本目录（`stock_kline_screen/`）
> - 依赖：`../stock_data_fetch/`（共享数据层）+ 它建好的 `shared.db`
> - 状态：4 个测试文件 **83 项全绿**；真实全链路（566 只候选池）尚未在源稳定窗口内跑完，见 §9.6

数据层本身的设计、源矩阵、六道闸、节流参数都在 **`../stock_data_fetch/README.md`**，
本文只讲这个工具：怎么跑、规则怎么落地、与原版差在哪、什么东西还没做对。

---

## 0. 一句话

K 线规则回答「什么时候启动」——**当天上穿 MA20 且当天放量**，而不是「站上 MA20」
这个可以连续成立几十天的状态。工具从基准日 S 往回找启动日 d\*，再用七条规则裁决，
最后给一份不带结论的候选研究池。

v2.0 改的只是「数据从哪来」，不是「怎么选」。

## 1. 与原版的逐条差异

### 1.1 取数：全部改走共享库

| 步骤 | 原版（westock CLI + JSON 缓存） | 本版（共享库） |
|---|---|---|
| 交易日历 | `trade-calendar`，4 年 | `hub.cal`（12 年，深交所权威腿） |
| 横截面 | 逐日 `screen condition`，**服务端按规则筛** | `hub.scan_many(need)`，**全市场**，涨幅过滤在本地 |
| ST | 服务端 `risk_st` 标签 | `scan` 行里的 `name` 含 `ST` |
| 次新 | 服务端四桶标签（5 天/3 月/1 年/3 年）并集 | `stock.list_date`（`profile` 域，**惰性**：只查裁决后的幸存者） |
| 日 K | 自管缓存 + 批内二分 + 5 轮退避 + 收尾核对 | `hub.ensure_many("kline", ...)`（配额/退避/覆盖全归 hub） |
| 行情/市值 | `quote --date` + `screen NegotiableMV` | `hub.ensure_many("quote", ...)`（当期一份） |
| 财务 | `data_finance` 三表 | `hub.ensure_many("finance", ...)`（20 期，单季列现成） |
| 行业 | `data_sector` 申万一级 + 二级 | `stock.industry`（**只有一级**，上游口径） |
| 净流入 / 市值比 | `MainNetFlow@d*` 展示列 | **砍掉**（见 §1.3） |

原版那套「批内二分 → 轮间退避 → 行情核对」的三道限频门（`KLINE_SPLIT_*` /
`KLINE_STALE_ROUNDS` / `_traded_on`）在 v2.0 里**整段消失**，因为它的每一层都在
解决「我自己抓的缓存不可信」：拆批是对付上游单次返回条数上限，退避是对付自己的
固定间隔，行情核对是对付自己的漏取。共享库用令牌桶 + 冷却闸 + coverage 覆盖判定
做同一件事，工具层再叠一层只会两套节流互相打架。

### 1.2 口径差异（会影响结果的，逐条给理由）

| # | 项 | 原版 | 本版 | 为什么可以这样 |
|---|---|---|---|---|
| 1 | 横截面筛选位置 | 服务端筛 + 本地复核 | **本地唯一裁决点** | hub 不做任何规则过滤，横截面就是全市场；原版复核服务端结果的代码从「防御」变成「唯一裁决点」 |
| 2 | ST 判定 | 服务端标签 | 名称含 `ST` | 覆盖 ST / \*ST / S\*ST / SST 全部形态；正常 A 股名称是纯中文 |
| 3 | 次新判定 | 四桶标签并集 | `list_date` 距今 < 3 年 | 四桶并集等价于「未满 3 年」；`list_date` 是静态事实 |
| 4 | 换手分位分母 | **d\* 日**流通市值 | **S 日**流通市值 | 库里 `quote` 是「当期一份」，历史某日市值没存；20 日均成交额对最多 N 个交易日的市值漂移不敏感（原版自己也是这么论证的，只是从 d\* 挪到 S） |
| 5 | 毛利率算法 | 优先上游 `GrossIncomeRatio_Q` | **一律本地算** `(营收单季−成本单季)/营收单季` | 库没存该比率列；`OperatingRevenue_Q`/`OperatingCost_Q` 与累计差分实测逐分一致，两个等价来源取哪个都对 |
| 6 | 防未来函数 | `InfoPublDate ≤ 基准日` 过滤 | **不过滤** | 当期运行（S = 最近交易日）时库里的最新期必然已披露，等价；**补跑历史日不等价**，见 §9.4 |
| 7 | 金融股「不适用」 | balancesheet `EnterpriseType` | `stock.is_financial` | 词表判定，`profile` 域一份三用（次新/行业/金融）。⚠️ 词表曾漏判「非银金融」，见 §1.5 |
| 8 | 盘中闸 | `_prepare` 里直接终止 | hub 闸 1 + `S <= hub.target` | 库够用就随时能跑；**联网才拦**（闸 1 语义），收盘闸由 `target` 表达 |
| 9 | CSV 列数 | 16 列 | **15 列** | 少「二级行业」——库里没有申万二级，拿一级凑数是编数据 |
| 10 | 缓存参数 | `--refresh` / `--refresh-industry` / `--prune-kline` / `--no-clean` / `--clean-dry-run` | **全删** | 缓存管理归 hub（coverage 闸 + GC）；要强制重取用 hub 的 `repair` 或删库 |
| 11 | 产物位置 | `csv_output/` + `database/` | `output/kline-screen/`，**只有两件产物** | 中间数据全在 `shared.db`，没有「中间文件」这个东西了 |

### 1.3 砍掉的东西及理由

| 砍掉的 | 原版用途 | 为什么砍 |
|---|---|---|
| 净流入、5 日净流入、市值比 | 展示列（v1.3 起已不参与筛选） | `SCAN_EXPR` 只能有一条条件（多一条就超 2 秒硬超时，见数据层 README），全市场口径下拿不到这两个字段；而它们**只展示、不裁决**，不值得为展示牺牲「能不能拿全」 |
| 「二级行业」列 | 展示列 | 共享库 `stock.industry` 只有上游一级口径 |
| 整套 volume 单位换算（`unit_from_prefix` / `infer_unit` / `volume_to_shares`） | 修「主板给手、科创板给股」的两可 | `kline.volume` 入库前已统一成**股**；留着反而误导后来人以为还要换 |
| `evaluation/`（前向评估 + 历史下载） | 评估名单的 5/10/20 日超额 | 不在本次重建范围；且评估要的是「全市场日线」，由共享库的 `kline`/`scan` 域天然支持，将来单写 |
| 自动清理 `dbclean` | 删 `database/` 里过期的中间缓存 | 中间数据在库里，GC 归 hub：`scan` 只留 30 天、`kline` 每只只留最近 400 根（`hub.prune_scan()` / `hub.prune_kline()`，每次跑完自动做） |

### 1.4 一字没动的部分

七条裁决规则与顺序、`find_start()` 的回扫上限与真上穿断言、`judge()` 的检查次序、
换手分位算法（严格小于的比例、星级边界、`< 15` 天判数据不足、`< 20` 只样本跳过硬过滤）、
毛利率三重护栏（环比递增 + 营收环比不为负 + 高于上年同季）、名单不设上限、
按分位升序展示、末尾三条硬断言。

### 1.5 为什么「一级行业」「毛利率改善」的取数源与日 K 无关（这是设计，不是缺陷）

2026-11-15 有人提过删掉这两列（理由：数据源与 CSV 其它列不同、与日 K 完全无关）。
**结论是不删**，理由记在这里，免得下次再被当成冗余清理掉。

**先说事实：这两列确实换源，而且必须换。** CSV 主体的 1–2、4–9、11–15 列来自
`scan` / `kline` / `quote` 三个域，都是**当日横截面或日 K 派生量**；而

| 列 | 域 | 上游 | 更新节奏 |
|---|---|---|---|
| 一级行业 | `profile` → `stock.industry` | westock `data_profile` | 一年可能不变一次 |
| 毛利率改善 | `finance` | westock 三表（单季列） | 一季度一次 |

**它们回答的是日 K 回答不了的问题。** 日 K 选的是「量价启动」——哪只票刚放量上穿
MA20。但如果只看这个，名单里会混进「纯资金推动、基本面在恶化」的票。
这两列是**正交的第二个维度**：

- 毛利率改善：这只正在启动的票，基本面在好转吗？（`是/否/无数据/不适用` + 数字证据）
- 一级行业：名单在行业上是怎么分布的？（这次 13 只散在 11 个行业，军工 2、汽车 2）

一列答「是不是好票的启动」，另一列答「这批启动集中在哪些板块」，两者都不参与裁决
（`output.py` 的参数块明写「只展示不参与裁决」）。删掉不会让选股更准，只会让**读名单时
少两组信息**。

**共享库更不该删 `stock.industry`。** 它不只喂这一列：

1. `pipeline._annotate_industry` — CSV 第 3 列（展示）
2. `pipeline._annotate_turnaround` → `turnaround.compute_turnaround(is_financial=...)` —
   金融股「不适用」豁免（**参与计算**）
3. `_check_new` — 次新判定同一批 `profile` 一起取，「一份三用」

删列会让第 2 项失去输入，金融股会被硬算毛利率。

#### 1.5.1 修掉的真 bug：`is_financial` 漏判「非银金融」

原词表是具体业态词 `("银行","保险","证券","多元金融","信托","期货","租赁")`，
判定用 `industry + name` 做子串匹配。问题在于 **A 股保险股的一级行业叫「非银金融」，
股票名里又没有"保险"二字**：

```
中国人寿  非银金融  → 漏判 False    ← 应为 True
中国平安  非银金融  → 漏判 False    ← 应为 True
中信证券  非银金融  → 碰巧 True     （名字里含"证券"，靠运气）
农业银行  银行      → True          （原本唯一靠行业名正确命中的）
```

后果不是标签错，是**下游算错**：险企 `OperatingCost_Q` 是 `NULL`（没有毛利率语义），
被判成非金融后硬算，CSV 输出「无数据：无毛利率数据」——看起来像数据缺失，实际是分类错。
2026-11-13 那次跑批里，中国人寿就带着这个错误标注进了名单。

**修法**：词表补 `"非银金融"` 做行业名直判，不再依赖股票名里恰好含业态词。
改完对库内 55 只重算 `is_financial`，修正 2 只（`sh600318` 新力金融、`sh601628` 中国人寿）。
同日一条用例进了 `tests/test_westock.py`（6 项），防止再退化。

> 若哪天要更准，正路是给 `profile` 域加申万二级/三级来源，而不是继续堆词表。
> 词表只做「毛利率/PE/PB 是否有意义」这一个判断，够用即止。

## 2. 一次运行走九步

`pipeline.run()` 的调用顺序（终端里的 `[n/6]` 是**沿用原版的六阶段编号**，
实际有九个子步骤；`[1/6]` 前缀没打，基准日信息直接以缩进打印）：

| # | 函数 | 干什么 | 终端标记 |
|---|---|---|---|
| 1 | `_prepare` | 校验参数、定基准日 S、算覆盖窗口 `need`（K = n+1 个交易日） | （无前缀） |
| 2 | `_load_cross` | `scan_many(need)` 取全市场，本地按涨幅区间粗筛，得 `pool` | `[2/6]` |
| 3 | `_load_labels` | 按日查 `scan_cached`，名称含 `ST` 的进排除集（**零额外请求**） | `[3/6]` |
| 4 | `_load_kline` | `ensure_many("kline", pool, 300 根/≥71 根)`，失败分两类处置 | `[4/6]` |
| 5 | `_select` | 逐只 `find_start` → `judge`，写下逐股去向 | `[5/6]` |
| 5b | `_check_new` | 只对幸存者取 `profile`，用 `list_date` 剔次新 | （无前缀） |
| 6 | `_enrich_market` | 取 `quote` → 算 20 日换手与池内分位 → 三条计数断言 | `[6/6]` |
| 7 | `_annotate_turnaround` | 取 `finance`，标注「毛利率改善」（只标注） | （无前缀） |
| 8 | `_annotate_industry` | 用 `profile.industry` 填一级行业，缺的记「未分类」 | （无前缀） |
| 9 | `_write` | 排序、CSV 原子写、result JSON、终端摘要，收尾 `hub.prune_scan()` | （无前缀） |

**为什么次新要挪到 5b 惰性做**：判次新要 `list_date`，对全池（可能 4000 只）逐只取
太贵；而裁决走到 ⑤ 之前，池子已被 ①②③④ 砍到几十只。原版用服务端四桶标签
一次拿全，v2.0 没这个便利，就用顺序换请求数。

末尾三条硬断言（不满足直接抛 `RuntimeError`，不产出不可信名单）：

```text
粗筛池 == 入选 + Σ剔除
剔除代码 ∩ 名单 == ∅
剔除代码 ∪ 名单 == 粗筛池（逐股都有去向）
```

外加 CSV 行数 == 名单数、产物必须落盘两条。

## 3. 七条规则

### 3.1 启动日 d\* 怎么找（`rules.find_start`）

```python
i = S 在该股 K 线中的下标                 # 找不到 S → "K线无 <S> 数据"
if i < MIN_HISTORY(70): 剔除              # 不足 71 根，算不了 MA60 也没回扫余量

# 从 S 往前连续统计「收盘 > MA20」的天数 up（MA 含当日）
for j 从 i 回扫到索引 20（回扫上限）:
    if 收盘[j] > MA20(j): up += 1
    else: break
if up == 0: 剔除                          # "未站上 MA20"

d* = i - (up - 1)                         # 连续站上段的起点
vcross = 成交量(d*) ÷ 前 5 个交易日（不含当日）均量

# 真上穿断言：d* 前一天必须不站在 MA20 上
if 收盘[d*-1] > MA20(d*-1): 剔除          # "非真上穿（连续站上 MA20 超过回扫上限）"
```

回扫上限是索引 20，所以「连续站上 MA20 超过约 51 天」的股票会得到
`非真上穿`——宁可漏掉，也不编一个不是上穿的日子当启动日。

### 3.2 逐条裁决（`rules.judge`）

检查顺序即剔除原因的输出顺序，**先便宜后贵**：

| # | 条件 | 口径 | 不通过时 |
|:--:|---|---|---|
| ⑦ | 新鲜度 | `age = i − ci ≤ N`（默认 N=4） | `⑦ 距启动X日 > N=4` |
| ② | 放量 | `vcross ≥ K_VOL(1.5)` | `② 启动日放量不足(x.xx<1.5)` |
| ③ | 日频 | d\* 在覆盖窗口内、且当日涨幅 ∈ `[0.5, 20.5]` | `③ 启动日未通过日频条件` / `③ 启动日涨幅X%不在[..]` |
| ④ | 均线结构 | `MA20(d*) ≥ MA60(d*)×0.95`；`MA20(d*) > MA20(d*−3)×0.99` | `④ 启动日 MA20 < MA60×0.95` 等 |
| ⑤ | 风控 | d\* 与 S **各查一次**：非 ST、非次新 | `⑤ ST` / `⑤ 次新（未满3年）` |
| ⑥ | 未破坏 | d\*+1 到 S 每根收盘都 > MA20 | 恒不触发，见下 |

三条容易误读的地方：

- **③ 有两条分支机构**。`d0 not in cross_by_day` 专指「启动日不在本次覆盖窗口」——
  `age` 是该股自己的 K 线索引差，不是市场交易日差；窗口内停牌时 d\* 的实际日期会早于
  `need[0]`，若不单列原因就会误记成「日频条件不通过」，污染追溯信息。
- **⑤ 要查两次**。d\* 当天不是 ST，不代表 S 日也不是；两个集合已经在手，复检成本为零。
- **⑥ 是定义性条件，不是独立过滤关**。`find_start` 从 S 往回走、跌破 MA20 即停，
  所以 [ci, i] 区间按定义每天在 MA20 上方，循环恒不触发、剔除数恒为 0。
  保留它只作防御性断言。

### 3.3 常量速查（`params.py`）

| 常量 | 值 | 用途 |
|---|---|---|
| `K_VOL` | 1.5 | 启动日放量倍数 |
| `CHG_LO` / `CHG_HI` | 0.5 / 20.5 | 启动日涨幅区间 %（北交所 30% 不覆盖，见 §9.5） |
| `C3_RATIO` | 0.95 | `MA20 ≥ MA60 × 该值`（v1.4 由 0.98 放宽） |
| `C2_TOL` | 0.01 | MA20 近 3 日跌幅容忍度 |
| `MA60_GAP` | 0.0 | `close/MA60` 上限，0 = 关闭 |
| `MIN_HISTORY` | 70 | `find_start` 的索引下界（含当日 ≥ 71 根） |
| `KLINE_BARS` | 300 | 向 hub 要的根数（= hub 的滚动深度） |
| `KLINE_MIN_BARS` | 71 | 门槛 = `MIN_HISTORY + 1` |
| `TURN_WINDOW` / `TURN_MIN_COVER` | 20 / 15 | 换手窗口 / 有效天数下限 |
| `TURN_PCT` / `TURN_MIN_N` / `TURN_MAX_N` | 0.0 / 5 / 30 | 硬过滤比例（0 = 只排序）/ 自动放宽 / 自动收紧 |
| `TURN_GM_REQUIRE_YOY` | True | ①「高于上年同季」护栏开关 |
| `NEW_STOCK_YEARS` | 3.0 | 次新 = 上市未满 3 年 |

### 3.4 逐股去向只有三种（`REJ_STAGE`）

| 阶段码 | 含义 |
|---|---|
| `FS` | `find_start()` 定位启动日失败（含「K线历史不足」） |
| `JD` | `judge()` 逐条裁决失败（含次新复检） |
| `TN` | 通过裁决但换手分位被硬过滤（仅 `--turn-pct > 0` 时产生） |

`reason_cat()` 把剔除原因里的**数字归一成 `#`**，只用于顶层统计聚合；
真实参数留在「剔除明细」的原文键里，逐股对应留在「剔除代码」里——
否则历史 JSON 无法反推当时的阈值。`MA20`/`MA60` 是写死在代码里的固定周期，
一并抹掉会让统计表读不出是哪条均线，因此放行 `MA\d+`。

## 4. 参数

```bash
cd ~/MyData/stock-value-invest-tool
python3 -m stock_kline_screen                      # 默认基准日 = 最近已收盘交易日，K=5
python3 -m stock_kline_screen --date 2026-11-06

```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--date` | 最近交易日 | 基准交易日；非交易日、未来日都会拒绝 |
| `--n` | `4` | 新鲜度窗口，**必须 = 扫描周期 − 1**（每周 K=5 用 4、每 3 日用 2、每日用 0） |
| `--k-vol` | `1.5` | 启动日放量倍数 |
| `--chg-lo` / `--chg-hi` | `0.5` / `20.5` | 启动日涨幅区间 |
| `--turn-pct` | `0.0` | 换手硬过滤保留池内最低比例，`[0,1)`；0 = 只排序标注，`0.4` = 只留 Q1–Q2 |
| `--turn-min` | `5` | 名单少于该数时自动放宽一档 |
| `--turn-max` | `30` | 名单多于该数时自动收紧一档 |
| `--ma60-gap` | `0.0` | `close/MA60` 上限，0 = 关闭 |
| `--db` | `$STOCKHUB_DB` 或 `~/MyData/stock-value-invest-tool/shared.db` | 透传给 `preflight` |

参数校验（`_prepare`，不合法直接 `CliError`）：`--n ≥ 0`、`--chg-lo ≤ --chg-hi`、
`--turn-pct ∈ [0,1)`、`--turn-min ≥ 0` 且 `--turn-max ≥ --turn-min`、
`S` 必须是交易日、`S ≤ hub.target`、基准日之前交易日数 ≥ `n+1`。

**退出码**：

| 码 | 含义 | 典型原因 |
|:--:|---|---|
| 0 | 成功 | |
| 1 | 参数/环境错误（`CliError`） | 非交易日、未来日、区间反了、窗口太短 |
| 2 | 数据不可信，主动中止（`RuntimeError`） | 基准日有成交却取不到 K 线、行情/流通市值缺失、计数不自洽 |
| 3 | 数据层错误（`HubError`） | 库版本不符、磁盘不足、preflight 闸未过 |

## 6. 失败语义（这一节比参数重要）

### 6.1 K 线取数失败分两类，处置完全不同

```python
depth_bad = {InsufficientDepth, HoleUnreachable}   # 上游只有这么多历史
hard      = {其余：PartialData / ThrottleTimeout / 源不可达}
```

| 类别 | 含义 | 处置 | 为什么 |
|---|---|---|---|
| `depth_bad` | 次新股只有几十根、长期停牌股中间有洞 | 记 `FS`「K线历史不足（上游只有部分历史）」**剔除，不中止** | 这不是「取数失败」，上游就该给这么多；原版用服务端四桶标签提前剔，v2.0 靠 `MIN_HISTORY=70` 在 `find_start` 里剔 |
| `hard`，且该股在 S 日横截面（有成交） | 真取不到 | **`RuntimeError` 中止整跑** | 基准日有成交却拿不到 K 线，绝不能当停牌放过去 |
| `hard`，且 S 日无成交 | 停牌 | 剔除 | 停牌股当日不在 `scan` 里，规则本来也选不进来 |

> 2026-11-14 真跑的教训：`sh601091`（上市两个月）只有 36 根 K 线，当时被当成硬失败，
> 直接把 566 只的候选池打断。现在它走 `depth_bad`，只剔它自己。
> 所以 `_load_kline` 里那句「失败分两类」不是分类学，是**整跑中止 vs 剔一只的区别**。

### 6.2 其他失败

| 失败点 | 处置 |
|---|---|
| `quote` 取数失败 | `RuntimeError` 中止——换手率的分母（流通市值）算不出来 |
| `circ_mv` 缺失（取到了但字段空） | `RuntimeError` 中止，同上 |
| `finance` 取数失败 | **降级**：毛利率列留空，`数据是否可用=false`，选股结果不受影响 |
| `profile` 取数失败 | 次新/行业/金融判定按「未知」处理，stderr 告警，不中止 |
| `prune_scan()` 失败 | 只跳过，不抛（收尾清理不该毁掉一份已经写盘的名单） |

原则：**凡是会让名单「少股」或「错股」的失败，一律中止**；凡是只影响标注列的，
一律降级 + 告警。宁可不出名单，也不出一份看起来正常、实际缺了几十只的名单。

## 7. 运行前提

1. **必须盘后**（收盘价、量能、成交额才定稿）。落库到 `S > hub.target` 会拒绝；
   `hub.target` 在收盘宽限（15:05）之后才推到今天，所以这个判断天然就是收盘闸。
2. **共享库必须可用**。`cli.main()` 先跑 `preflight()` 过六道闸：盘中（联网才拦）/
   库可用 / 版本 / `PRAGMA` 回读 / 日历 / 空间。库不存在会自动建，版本不符直接拒绝启动。
3. **库里的覆盖要够**。缺的部分由 `ensure_many` 现场补——这一步会联网、会吃配额、
   会在源被限频时变慢。首次跑（566 只 × 300 根）是最慢的一次。

## 9. 已知限制

### 9.0 价格一律**不复权**（2026-11-15 确认保留）

MA20/MA60、5 日涨幅、启动日涨幅全用**不复权**（raw）收盘价。取舍明确：

- **好处**：库内只存 raw，是唯一真相；复权需要 dividend 表完整，**缺一条就静默
  算错**（因子恒为 1.0 时 qfq 悄悄等于 raw，比偏差更难发现）。选股是同一交易日的
  横截面比较，全池同口径，排序基本不受影响。
- **代价**：除权日附近，用前复权的那套代码会和我这里差一点点。实测 2026-11-13
  名单里的 `sh601288 农业银行`（2026-10-21 除息 0.13 元）：原代码用 qfq 算 MA20
  = 7.358，这里 raw 算 7.371，**距 MA20% 差 0.16pp**（+0.16% vs −0.014%）。
  38 只里只有它越过了 `--above-ma20` 的边界，其余 37 只完全一致。

要看复权口径的信号（比如判断"股价是否站上均线"），用 `stock_judge_top`——
那边是 `raw × 因子` 本地算 qfq，锚点 = 基准日。

### 9.1 池内换手分位的分母（**2026-11-14 已修**）

修复前的行为：`_enrich_market` 只为**入选股**取 `quote`（`circ_mv`），但 `cap_snapshot`
按整个 `st["pool"]` 建字典——池内非入选股市值是 `None`，`turnover20()` 返回
`(None, 0)`，进不了 `pool_t`。后果是分母缩成「入选名单」：`池内样本` ≈ 入选数、
`turn20_rank` 变成名单内部的高低、`--turn-pct` 在名单不足 20 只时**永远不触发**。
是拿原版 11-13 那一期（粗筛池 4302 只）对照时才暴露的。

现在：`quote` 对整个 `st["pool"]` 取（566 只 ≈ 15 批，适配器内部 40 只一批聚合），
`池内样本` 就是「池里算得出 20 日换手的只数」。两类缺市值分开处置：

| 缺谁 | 处置 | 理由 |
|---|---|---|
| 入选股 | `RuntimeError` 中止 | 名单里的换手列会算错 |
| 池内非入选股 | 只退出分位分母，stderr 报数 | 不影响任何入选股的换手值，只缩小分母，而分母已经打印出来了 |

`result` 的 `参数` 里新增 `换手分位口径` 一行，写明分母是粗筛池的多少只。
测试补了 5 条（`test_pipeline` 的两组新用例）：池内样本 == 25 而非入选数、
`quote` 是对全池调的、分位确实落在 Q1、`--turn-pct` 真的产生 `TN` 剔除。

### 9.2 没有「二级行业」「净流入」「市值比」

见 §1.3。补二级行业得先给 hub 加来源，不能拿一级凑数。

### 9.3 腾讯通道没有成交额 → `amount = 0`

`kline` 表只有东财 `fqt=0` 有成交额；tencent 备源没有该字段，写入时 `amount` 落 0
（`api._write_kline` 里有意的 `or 0.0`）。换手计算在 `amount <= 0` 时退回
`close × volume`，所以**结果不会错，但精度略降**（用收盘价估算成交额）。
靠 `kline.src` 可以区分一行是哪个源来的。

### 9.4 补跑历史基准日：毛利率可能用到「S 之后才披露」的报告期

当期运行（S = 最近交易日）没有问题：库里最新期必然已披露。但 `--date` 补跑历史日时，
`turnaround` 不再按 `InfoPublDate ≤ S` 过滤（库里没存披露日），会把更晚的报告期用上。
`_annotate_turnaround` 在 `S != hub.target` 时会打 stderr 提示，**不静默**。
真要修，得给 `finance` 域加披露日列——那是数据层的改动。

### 9.5 北交所口径

`CHG_HI=20.5` 只覆盖主板 10% 与创业板/科创板 20%，北交所 30% 不覆盖。
粗筛池里出现 `bj*` 时代码会在 stderr 告警，应改用 `--chg-hi 30.5`。

### 9.6 真实全链路还没跑完过

单元与端到端（`FakeHub`）测试全绿，但 566 只候选池的**真上游**全链路尚未跑通，
卡在源不稳定：东财 `push2his` 2026-11-14 20:15 起持续拒连（40 分钟量级），
腾讯 web 通道在密集请求后也开始回跳转页。腾讯备源已在 5 只票 × 300 根上与东财
`fqt=0` 逐点同值（bad=0），所以一旦源可用，链路应该能一次跑通——但这句是推断，
不是实测。**没跑通前不要拿它的名单当真。**

### 9.7 规则本身的前提没有收益层面的实证

参数依据是覆盖率、池子规模、阈值敏感性，不是收益率优化。名单是候选研究池，
不是买卖建议。名单规模历史区间 2~155 只，中位数约 18 只，普涨周会明显变长。
